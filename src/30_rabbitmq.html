Sổ tay RabbitMQ

Message broker cho hàng đợi công việc và định tuyến sự kiện: exchange, queue type, confirm/ack, dead-letter, retry. Mỗi phần có ví dụ cho cả NestJS và Java, cùng các pattern hay dùng trong production.

RabbitMQ là gì

RabbitMQ là message broker: producer gửi message tới broker, broker định tuyến vào các queue, consumer lấy message ra xử lý và xác nhận. Hai bên không cần biết nhau, không cần online cùng lúc. Giao thức chính là AMQP 0-9-1; từ 4.x, AMQP 1.0 được hỗ trợ sẵn (không cần plugin) và được docs khuyên dùng cho ứng dụng mới.

  1. ProducerPublish message kèm routing key tới một exchange. Producer không gửi thẳng vào queue.
  2. ExchangeSo routing key với các binding để quyết định message vào queue nào (0, 1 hay nhiều queue).
  3. QueueLưu message theo thứ tự FIFO cho tới khi được consumer xác nhận.
  4. ConsumerNhận message (push), xử lý, rồi ack hoặc nack.

Thay đổi quan trọng ở 4.x

  • 4.0: bỏ hẳn classic mirrored queue. Muốn sao chép dữ liệu giữa các node thì dùng quorum queue hoặc stream. delivery-limit mặc định của quorum queue là 20.
  • 4.3: Khepri (dựa trên Raft) là kho metadata duy nhất, thay Mnesia. Quorum queue có thêm delayed retry, priority 0–31, consumer timeout. Global QoS bị tắt mặc định.
  • 4.4: đặt replica quorum queue theo availability zone, delayed message qua x-opt-delivery-time.

Thuộc tính khi khai báo queue: durable (còn sau khi broker khởi động lại), exclusive (chỉ một connection, tự xóa khi connection đóng), auto-delete (xóa khi consumer cuối hủy). Khai báo lại queue với thuộc tính khác sẽ bị lỗi 406 PRECONDITION_FAILED.

Policy hơn x-arguments

Các tham số đổi được (TTL, max-length, DLX, delivery-limit) nên đặt bằng policy trên broker thay vì hard-code x-arguments trong code: đổi policy không cần xóa queue. Riêng x-queue-type, x-max-priority, x-single-active-consumer chỉ đặt được lúc khai báo.

rabbitmqctl set_policy orders-dlx "^orders\." \
  '{"dead-letter-exchange":"orders.dlx","delivery-limit":5,"max-length":1000000,"overflow":"reject-publish"}' \
  --apply-to quorum_queues

Độ tin cậy: confirm, ack, prefetch

Không mất message cần đủ ba thứ: queue durable (hoặc quorum) + message persistent, publisher confirm ở phía gửi, và manual ack ở phía nhận.

Publisher confirms

Bật confirm.select trên channel; broker gửi basic.ack khi mọi queue đích đã nhận message (với quorum queue là khi đa số replica đã ghi). basic.nack từ broker nghĩa là message không được nhận, producer phải gửi lại. Confirm có thể về không theo thứ tự publish.

Consumer acknowledgements

LệnhÝ nghĩa
basic.ack(tag, multiple)Xử lý xong, xóa message. multiple=true ack mọi tag ≤ tag này trên channel.
basic.nack(tag, multiple, requeue)Từ chối. requeue=true: trả lại queue; false: đẩy sang DLX nếu có, không thì bỏ.
basic.reject(tag, requeue)Như nack nhưng một message.
  • Channel/connection đóng khi còn message chưa ack thì các message đó được trả về queue với cờ redelivered. Vì vậy consumer luôn có thể nhận trùng (at-least-once).
  • Delivery tag gắn với channel: ack trên channel khác hoặc ack hai lần sẽ làm channel bị đóng.
  • Auto-ack ("fire and forget") mất message khi consumer chết giữa chừng; chỉ dùng cho dữ liệu không quan trọng.

Prefetch (basic.qos)

prefetch_count giới hạn số message đã giao mà chưa ack cho mỗi consumer. Docs gợi ý 100–300 cho thông lượng tốt; 1 an toàn nhất nhưng chậm; hàng nghìn dễ làm consumer tràn RAM. Quorum queue giới hạn tối đa 2.000. Với việc xử lý lâu (gọi API ngoài vài giây), đặt nhỏ (10–50) để chia đều giữa các consumer.

Dead letter, TTL, giới hạn độ dài, retry

Message bị "dead-letter" (chuyển sang DLX) khi: bị nack/reject với requeue=false, hết TTL, queue vượt độ dài (overflow drop-head), hoặc quorum queue vượt delivery-limit. Hết hạn cả queue (x-expires) thì không dead-letter.

Tham số (x-arg / policy)Tác dụng
x-dead-letter-exchange / dead-letter-exchangeExchange nhận message chết
x-dead-letter-routing-keyĐổi routing key khi dead-letter (mặc định giữ key gốc)
x-message-ttl / message-ttlTTL message (ms). Thuộc tính expiration đặt cho từng message; lấy giá trị nhỏ hơn.
x-expiresXóa queue nếu không được dùng trong N ms
x-max-length, x-max-length-bytes, x-overflowGiới hạn; overflow = drop-head (mặc định), reject-publish, reject-publish-dlx (classic)
x-delivery-limit (quorum)Giao quá N lần thì dead-letter. Mặc định 20.
dead-letter-strategy: at-least-once (policy, quorum)Không mất message khi dead-letter (mặc định là at-most-once). Cần overflow: reject-publish.
x-delayed-retry-type/min/max (quorum, 4.3+)Trả lại queue sau một khoảng chờ tăng dần: min(min × delivery_count, max)

Message chết mang header x-death (lý do: rejected, expired, maxlen, delivery_limit; số lần; queue gốc), rất hữu ích để debug và đếm số lần retry.

Single active consumer, priority, streams

  • Single active consumer (x-single-active-consumer: true): nhiều consumer đăng ký nhưng chỉ một nhận message, các consumer khác chờ thay thế khi nó chết. Giữ được thứ tự xử lý mà vẫn có dự phòng.
  • Priority: classic cần x-max-priority (docs khuyên 2–4 mức); quorum từ 4.3 có sẵn 32 mức (0–31), message không đặt priority được tính là 4. Priority nghiêm ngặt có thể làm message ưu tiên thấp bị "đói".
  • Stream: khai báo x-queue-type: stream, retention bằng x-max-age (ví dụ 7D) và x-max-length-bytes; consumer chọn vị trí đọc bằng x-stream-offset (first, last, next, số offset, timestamp). Super stream chia stream thành nhiều partition giống Kafka.

Dùng trong NestJS

Cách 1: @golevelup/nestjs-rabbitmq lib

Linh hoạt nhất cho exchange/routing key kiểu topic; đây là thư viện service api/ của bạn đang dùng.

import { RabbitMQModule } from '@golevelup/nestjs-rabbitmq';

@Module({
  imports: [
    RabbitMQModule.forRootAsync({
      inject: [ConfigService],
      useFactory: (c: ConfigService) => ({
        uri: c.getOrThrow('AMQP_URL'),
        exchanges: [
          { name: 'fraud', type: 'topic' },
          { name: 'fraud.dlx', type: 'topic' },
        ],
        channels: { main: { prefetchCount: 50, default: true } },
        connectionInitOptions: { wait: false },   // không chặn khởi động khi broker chưa sẵn sàng
        enableControllerDiscovery: true,
      }),
    }),
  ],
  providers: [OrderConsumer, OrderPublisher],
})
export class RabbitModule {}

import { AmqpConnection, Nack, RabbitSubscribe } from '@golevelup/nestjs-rabbitmq';
import { ConsumeMessage } from 'amqplib';

@Injectable()
export class OrderConsumer {
  private readonly logger = new Logger(OrderConsumer.name);

  @RabbitSubscribe({
    exchange: 'fraud',
    routingKey: ['order.created', 'order.updated'],
    queue: 'risk.orders',
    queueOptions: {
      durable: true,
      arguments: { 'x-queue-type': 'quorum', 'x-dead-letter-exchange': 'fraud.dlx', 'x-delivery-limit': 5 },
    },
  })
  async handle(msg: OrderEvent, raw: ConsumeMessage) {
    try {
      await this.risk.score(msg);
      // trả về undefined → thư viện ack
    } catch (e) {
      this.logger.error(`order ${msg.orderId} failed`, e as Error);
      return new Nack(false);          // không requeue → sang DLX
    }
  }
}

@Injectable()
export class OrderPublisher {
  constructor(private readonly amqp: AmqpConnection) {}

  created(order: OrderEvent) {
    return this.amqp.publish('fraud', 'order.created', order, {
      persistent: true,
      messageId: `order.created:${order.orderId}`,   // để consumer chống trùng
      contentType: 'application/json',
    });
  }
}

Cách 2: @nestjs/microservices (Transport.RMQ)

Có sẵn trong Nest, cấu hình đơn giản nhưng mỗi microservice gắn với một queue và ít kiểm soát exchange hơn. Ví dụ đầy đủ ở tab NestJS, mục Microservices.

Dùng trong Java

Java client chính thức (com.rabbitmq:amqp-client) lib

ConnectionFactory f = new ConnectionFactory();
f.setUri(System.getenv("AMQP_URL"));
f.setAutomaticRecoveryEnabled(true);                  // tự kết nối lại khi mất mạng

Connection conn = f.newConnection("risk-service");    // dùng lâu dài, không mở/đóng liên tục
Channel ch = conn.createChannel();                    // channel KHÔNG thread-safe: mỗi thread một channel

ch.exchangeDeclare("fraud", BuiltinExchangeType.TOPIC, true);
ch.queueDeclare("risk.orders", true, false, false,
    Map.of("x-queue-type", "quorum", "x-dead-letter-exchange", "fraud.dlx"));
ch.queueBind("risk.orders", "fraud", "order.*");

// consumer: manual ack
ch.basicQos(50);
DeliverCallback onMessage = (tag, delivery) -> {
    long deliveryTag = delivery.getEnvelope().getDeliveryTag();
    try {
        handle(new String(delivery.getBody(), StandardCharsets.UTF_8));
        ch.basicAck(deliveryTag, false);
    } catch (Exception e) {
        ch.basicNack(deliveryTag, false, false);      // sang DLX
    }
};
ch.basicConsume("risk.orders", false, onMessage, consumerTag -> { });

// publisher confirms
Channel pub = conn.createChannel();
pub.confirmSelect();
AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
    .contentType("application/json")
    .deliveryMode(2)                                  // persistent
    .messageId("order.created:" + orderId)
    .build();
pub.basicPublish("fraud", "order.created", props, json.getBytes(StandardCharsets.UTF_8));
pub.waitForConfirmsOrDie(5_000);                      // đơn giản; thông lượng cao thì dùng addConfirmListener

Work queue và Publish/Subscribe

Work queue (competing consumers)

Nhiều consumer cùng đọc một queue: mỗi message chỉ một consumer nhận, tải tự chia đều. Muốn tăng tốc thì thêm consumer. Đặt prefetch nhỏ để consumer chậm không ôm nhiều việc.

Publish/Subscribe

Mỗi service có queue riêng bind vào cùng một exchange; một sự kiện được copy tới mọi service quan tâm, và trong mỗi service lại là work queue.

                           ┌── binding order.* ──► queue risk.orders      ► risk-service ×3
order.created ► [fraud] ───┼── binding order.# ──► queue analytics.orders ► analytics ×1
   (topic)                 └── binding *.created ► queue audit.created    ► audit ×1

Đặt tên queue theo <service>.<mục đích> và routing key theo <thực thể>.<sự kiện> giúp đọc topology dễ dàng.

Retry có độ trễ và parking lot

Lỗi tạm thời (API ngoài 503) cần thử lại sau một lúc; lỗi vĩnh viễn (dữ liệu sai) cần đưa ra chỗ riêng để người xem. Không bao giờ nack(requeue=true) ngay lập tức: message sẽ quay vòng liên tục và làm nghẽn queue.

Cách 1: quorum queue delayed retry (4.3+)

rabbitmqctl set_policy risk-retry "^risk\." \
  '{"delayed-retry-type":"failed","delayed-retry-min":1000,"delayed-retry-max":60000,"delivery-limit":6,"dead-letter-exchange":"fraud.parking"}' \
  --apply-to quorum_queues
# consumer chỉ cần nack(requeue=true): broker tự giữ lại 1s, 2s, 3s… tối đa 60s; quá 6 lần → parking

Cách 2: retry queue có TTL (chạy được mọi phiên bản)

risk.orders ──nack──► [fraud.retry] ─► risk.orders.retry.10s (x-message-ttl=10000,
     ▲                                     x-dead-letter-exchange=fraud,
     └──────────── hết TTL quay về ────────  x-dead-letter-routing-key=order.created)
consumer đọc x-death count ≥ 5 ──► publish sang risk.orders.parking rồi ack

const deaths = (raw.properties.headers?.['x-death'] as Array<{ count: number }> | undefined) ?? [];
const attempts = deaths.reduce((n, d) => n + d.count, 0);

if (isPermanent(err) || attempts >= 5) {
  await this.amqp.publish('fraud.parking', raw.fields.routingKey, msg, { headers: { error: String(err) } });
  return;                                  // ack bản gốc
}
return new Nack(false);                    // sang retry queue, quay lại sau TTL

Idempotent consumer và thứ tự

RabbitMQ giao at-least-once: consumer phải chịu được message trùng. Gắn messageId ổn định ở producer, lưu lại id đã xử lý ở consumer.

async handle(msg: OrderEvent, raw: ConsumeMessage) {
  const id = raw.properties.messageId;
  const first = await this.redis.set(`processed:${id}`, '1', 'EX', 7 * 86_400, 'NX');
  if (!first) return;                       // đã xử lý, ack luôn
  try {
    await this.risk.score(msg);
  } catch (e) {
    await this.redis.del(`processed:${id}`); // cho phép thử lại
    return new Nack(false);
  }
}

Cách bền hơn: ghi id vào DB cùng transaction với kết quả (unique index), hoặc thiết kế thao tác tự nhiên idempotent (upsert theo khóa nghiệp vụ).

Giữ thứ tự

  • Một queue + một consumer giữ thứ tự; nhiều consumer hoặc requeue làm mất thứ tự.
  • Cần thứ tự theo từng khóa (mỗi shop) mà vẫn song song: dùng consistent hash exchange (plugin) chia theo khóa sang N queue, mỗi queue bật single active consumer; hoặc super stream.

RPC qua RabbitMQ

Client gửi request kèm replyTo (queue trả lời) và correlationId; server xử lý rồi publish kết quả vào replyTo. Dùng khi cần request/response qua broker (cân bằng tải tự nhiên, không cần service discovery). Phải luôn có timeout.

// @golevelup: phía server
@RabbitRPC({ exchange: 'fraud', routingKey: 'risk.score', queue: 'risk.rpc' })
score(req: { orderId: string }) {
  return this.risk.score(req.orderId);                 // giá trị trả về được gửi về replyTo
}

// phía client
const res = await this.amqp.request<{ score: number }>({
  exchange: 'fraud', routingKey: 'risk.score', payload: { orderId }, timeout: 5_000,
});

Với Spring: rabbitTemplate.convertSendAndReceive(...). Nếu hai service đều online và cần gọi đồng bộ, HTTP/gRPC thường đơn giản hơn RPC qua broker.

Checklist production

  • Cụm số node lẻ (3, 5): quorum queue cần đa số node. Từ 4.3 (bỏ Mnesia), cluster_partition_handling không còn tác dụng, hãy xóa khỏi cấu hình; bản ≤ 4.2 thì pause_minority an toàn hơn ignore (mặc định), không dùng cho cụm 2 node.
  • Dùng quorum queue cho dữ liệu quan trọng; chỉ khai báo queue durable hoặc exclusive.
  • Bật publisher confirm + manual ack; message persistent.
  • Prefetch khoảng 100–300 (nhỏ hơn cho việc xử lý lâu).
  • Mọi queue nghiệp vụ có DLX và giới hạn độ dài; cấu hình bằng policy.
  • Connection dùng lâu dài, tách connection publish và consume; mỗi thread một channel; bật tự kết nối lại.
  • Xóa user guest, mỗi ứng dụng một user, mỗi môi trường một vhost; bật TLS.
  • vm_memory_high_watermark.relative 0.4–0.7; disk_free_limit đặt cỡ bằng mức watermark bộ nhớ (mặc định 50MB quá thấp cho production). Alarm có hiệu lực toàn cụm: một node vượt ngưỡng là publisher ở mọi node bị chặn.
  • Heartbeat 5–20 giây; idle timeout của load balancer phải lớn hơn khoảng heartbeat.
  • Quorum queue luôn có DLX qua policy: vượt delivery-limit (mặc định 20) mà không có DLX thì message bị bỏ.
  • Giám sát độ dài queue, số message chưa ack, tốc độ publish/deliver/ack (Prometheus plugin).
