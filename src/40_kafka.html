Tổng hợp từ kafka.apache.org (bản 4.4)

Sổ tay Kafka

Nền tảng event streaming dạng log phân tán: topic, partition, consumer group, các mức đảm bảo giao nhận, transaction và share group. Có ví dụ cho NestJS, Java client, Spring Kafka, Kafka Streams và các pattern thường gặp.

Kafka là gì

Kafka lưu sự kiện vào các log chỉ ghi nối (append-only), chia partition và sao chép trên nhiều broker. Khác message broker truyền thống, message không bị xóa khi đọc: mỗi consumer group tự giữ vị trí (offset) của mình, nhiều hệ thống đọc cùng dữ liệu độc lập, và có thể đọc lại từ quá khứ trong thời gian retention.

Thay đổi ở 4.x

  • 4.0: bỏ ZooKeeper, chỉ chạy KRaft (controller dùng Raft). Giao thức rebalance mới cho consumer (KIP-848) chính thức, client bật bằng group.protocol=consumer. linger.ms mặc định đổi từ 0 thành 5. Broker cần Java 17; client cần Java 11 trở lên.
  • 4.1: share group (Queues for Kafka, KIP-932) ở dạng preview.
  • 4.2: share group sẵn sàng cho production; giao thức rebalance mới cho Kafka Streams (KIP-1071).
  • 4.4: share group có dead-letter queue (KIP-1191); broker.id deprecated, dùng node.id.

  P0: [0][1][2][3][4] ─────────────────────►  consumer A (P0, P1)      ─► consumer X (P0, P1, P2)
  P1: [0][1][2]       ─────────────────────►
  P2: [0][1][2][3]    ─────────────────────►  consumer B (P2)

Số partition

Số consumer hoạt động trong một group tối đa bằng số partition; consumer thừa sẽ ngồi chơi. Tăng partition sau này làm thay đổi ánh xạ key → partition (mất thứ tự theo key với dữ liệu cũ), nên hãy chọn dư ngay từ đầu.

Thứ tự xử lý quyết định ngữ nghĩa: commit trước khi xử lý là at-most-once (có thể mất); xử lý xong rồi commit là at-least-once (có thể trùng, cách phổ biến nhất). Auto-commit thực chất commit offset của lần poll trước, nên vẫn là at-least-once nếu bạn xử lý xong trước lần poll kế tiếp.

Xử lý chậm

Nếu một batch mất lâu hơn max.poll.interval.ms, consumer bị coi là chết, partition chuyển cho consumer khác và batch bị xử lý lại. Giảm max.poll.records hoặc tăng interval cho việc nặng.

Đảm bảo giao nhận và exactly-once

MứcCách đạt
At-most-onceCommit offset trước khi xử lý
At-least-onceProducer acks=all + idempotence; consumer xử lý xong mới commit; consumer idempotent
Exactly-once (Kafka → Kafka)Transaction: ghi output và commit offset input trong cùng một transaction; consumer đọc với read_committed

Exactly-once của Kafka chỉ bao trùm dữ liệu nằm trong Kafka. Khi xử lý có tác động ra ngoài (ghi DB, gọi API), vẫn cần consumer idempotent hoặc lưu offset cùng transaction với DB.

Retention, compaction và share group

  • Retention theo thời gian/dung lượng (cleanup.policy=delete): xóa segment cũ theo retention.ms / retention.bytes của topic.
  • Log compaction (cleanup.policy=compact): giữ ít nhất bản ghi mới nhất cho mỗi key. Record value null là tombstone (đánh dấu xóa), bị dọn sau delete.retention.ms (mặc định 24 giờ). Dùng cho topic dạng "bảng trạng thái": cấu hình shop, số dư, snapshot.
  • Có thể kết hợp compact,delete.

Share group (Queues for Kafka) 4.2

Consumer group thường gắn mỗi partition cho một consumer. Share group cho phép nhiều consumer cùng đọc một partition, ack từng record và đếm số lần giao, giống work queue của RabbitMQ. Hợp với việc xử lý từng record độc lập mà không cần thứ tự; số consumer không còn bị giới hạn bởi số partition.

Dùng trong NestJS

@nestjs/microservices có Transport.KAFKA dựa trên thư viện kafkajs. Lưu ý KafkaJS ít được bảo trì gần đây; Confluent phát hành @confluentinc/kafka-javascript có API tương thích KafkaJS nếu bạn cần client được hỗ trợ chính thức.

const app = await NestFactory.create(AppModule);
app.connectMicroservice({
  transport: Transport.KAFKA,
  options: {
    client: { clientId: 'risk', brokers: process.env.KAFKA_BROKERS!.split(',') },
    consumer: { groupId: 'risk', sessionTimeout: 45_000 },
    run: { autoCommit: false },                // tự commit sau khi xử lý
    subscribe: { fromBeginning: false },
  },
});
await app.startAllMicroservices();
await app.listen(3000);

@Controller()
export class OrdersConsumer {
  @EventPattern('orders.created')
  async onCreated(@Payload() order: OrderEvent, @Ctx() ctx: KafkaContext) {
    const { offset } = ctx.getMessage();
    await this.risk.score(order);
    await ctx.getConsumer().commitOffsets([
      { topic: ctx.getTopic(), partition: ctx.getPartition(), offset: (BigInt(offset) + 1n).toString() },
    ]);
  }
}

@Module({

@Injectable()

  async onModuleInit() { await this.kafka.connect(); }

  created(order: OrderEvent) {
    // key = shop → mọi sự kiện của một shop vào cùng partition, giữ thứ tự
    return this.kafka.emit('orders.created', { key: order.shop, value: JSON.stringify(order) });
  }
}

Kafka Streams

Thư viện xử lý luồng chạy ngay trong ứng dụng Java (không cần cluster riêng): filter, join, aggregate, window, có state store và exactly-once.

StreamsBuilder b = new StreamsBuilder();
b.stream("orders.created", Consumed.with(Serdes.String(), orderSerde))      // key = shop
 .filter((shop, order) -> order.flagged())
 .groupByKey()
 .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5)))
 .count()
 .toStream((windowedShop, count) -> windowedShop.key())
 .filter((shop, count) -> count >= 10)
 .to("alerts.fraud-burst", Produced.with(Serdes.String(), Serdes.Long()));

Properties s = new Properties();
s.put(StreamsConfig.APPLICATION_ID_CONFIG, "fraud-burst-detector");
s.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
s.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG, StreamsConfig.EXACTLY_ONCE_V2);
new KafkaStreams(b.build(), s).start();

Chọn key và thiết kế topic

  • Key = thực thể cần giữ thứ tự: orderId, shop, customerId. Mọi sự kiện của cùng thực thể vào cùng partition, xử lý tuần tự.
  • Tránh key quá "nóng" (một shop chiếm 50% traffic) gây lệch tải partition. Có thể ghép key: shop:orderId khi chỉ cần thứ tự theo đơn.
  • Đặt tên topic theo <domain>.<sự kiện> hoặc <domain>.<thực thể>.v1; đổi schema không tương thích thì tạo topic phiên bản mới.
  • Dùng schema (Avro/Protobuf/JSON Schema + Schema Registry) để producer và consumer tiến hóa độc lập mà không làm vỡ nhau.
  • Sự kiện nên tự đủ thông tin (event-carried state) để consumer không phải gọi ngược lại service gốc.

Retry topic và dead-letter topic

Kafka không có nack/requeue: nếu một record lỗi mà không commit, consumer bị kẹt ở đó và cả partition dừng lại. Giải pháp là chuyển record lỗi sang topic khác và commit để đi tiếp.

orders.created ─lỗi─► orders.created-retry-1 (chờ 1s) ─lỗi─► orders.created-retry-2 (chờ 10s) ─lỗi─► orders.created-dlt
      ▲                         │                                   │
      └──── thành công: commit ─┴───────────────────────────────────┘     dlt: lưu lại, cảnh báo, xử lý tay

// Spring Kafka tự tạo retry topic + DLT
@RetryableTopic(attempts = "4", backoff = @Backoff(delay = 1000, multiplier = 10),
                exclude = { ValidationException.class })          // lỗi vĩnh viễn: thẳng sang DLT
@KafkaListener(topics = "orders.created", groupId = "risk")
void on(OrderEvent e) { risk.score(e); }

@DltHandler
void dlt(OrderEvent e, @Header(KafkaHeaders.EXCEPTION_MESSAGE) String error) {
    alerts.send("DLT: " + e.orderId() + " " + error);
}

Ở NestJS, tự publish sang topic *.retry / *.dlt kèm header số lần thử và lỗi, rồi commit offset gốc. Retry topic làm mất thứ tự theo key; nếu thứ tự quan trọng, hãy retry tại chỗ vài lần (backoff ngắn) trước khi đẩy sang DLT.

Consume–transform–produce exactly-once

producerProps.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "risk-scorer-" + instanceId);
consumerProps.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");
consumerProps.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);

producer.initTransactions();
while (running) {
    var records = consumer.poll(Duration.ofMillis(500));
    if (records.isEmpty()) continue;
    producer.beginTransaction();
    try {
        Map offsets = new HashMap<>();
        for (var r : records) {
            producer.send(new ProducerRecord<>("orders.scored", r.key(), score(r.value())));
            offsets.put(new TopicPartition(r.topic(), r.partition()), new OffsetAndMetadata(r.offset() + 1));
        }
        producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());   // commit input cùng output
        producer.commitTransaction();
    } catch (ProducerFencedException e) {
        producer.close();                    // có instance khác cùng transactional.id: dừng
        throw e;
    } catch (KafkaException e) {
        producer.abortTransaction();
        rewindToCommitted(consumer);         // seek về offset đã commit rồi xử lý lại
    }
}

Kafka Streams làm sẵn toàn bộ việc này khi đặt processing.guarantee=exactly_once_v2.

Outbox + CDC và idempotent consumer

Ghi DB rồi gửi Kafka có thể lệch nhau (dual write). Pattern chuẩn: ghi sự kiện vào bảng/collection outbox trong cùng transaction với dữ liệu; Debezium (Kafka Connect) đọc change log của DB (binlog, WAL, MongoDB change stream) và đẩy vào Kafka. Không cần code relay tự viết như ở tab NestJS.

{
  "name": "orders-outbox",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "db", "database.dbname": "shop", "topic.prefix": "shop",
    "table.include.list": "public.outbox",
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
    "transforms.outbox.route.by.field": "aggregate_type"
  }
}

Phía consumer: at-least-once nên phải chống trùng. Lưu (topic, partition, offset) hoặc eventId vào bảng processed với unique key trong cùng transaction với kết quả xử lý, hoặc dùng upsert theo khóa nghiệp vụ.

Compacted topic làm bảng trạng thái

Publish trạng thái mới nhất của mỗi thực thể với key = id vào topic compacted. Service khác đọc topic từ đầu lúc khởi động để dựng cache cục bộ, rồi tiếp tục cập nhật theo sự kiện mới, không cần gọi API service gốc. Kafka Streams gọi đây là KTable/GlobalKTable.

GlobalKTable settings =
    builder.globalTable("shop.settings", Consumed.with(Serdes.String(), settingsSerde));

builder.stream("visits", Consumed.with(Serdes.String(), visitSerde))
    .join(settings, (visitId, visit) -> visit.shop(),                 // tra cấu hình shop cho mỗi visit
          (visit, cfg) -> evaluate(visit, cfg))
    .to("visits.evaluated");

Xóa một thực thể: gửi tombstone (key + value null).

Checklist production

  • Ít nhất 3 broker; topic quan trọng replication.factor=3, min.insync.replicas=2, producer acks=all.
  • Giữ unclean.leader.election.enable=false (mặc định) để không mất dữ liệu khi failover.
  • Chọn số partition theo thông lượng mục tiêu và số consumer tối đa; khó giảm về sau.
  • Consumer tắt auto-commit cho việc quan trọng, xử lý idempotent, có retry topic + DLT.
  • Theo dõi consumer lag theo group/partition; cảnh báo khi lag tăng liên tục.
  • Dùng schema registry; quy định tương thích (BACKWARD) cho từng topic.
  • Bật TLS + SASL, ACL theo từng service; không để auto.create.topics.enable ở production.
  • Client mới dùng group.protocol=consumer; dùng group.instance.id cho deployment rolling ít rebalance.
