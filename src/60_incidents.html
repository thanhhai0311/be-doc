Runbook xử lý sự cố

Sự cố production

Các lỗi hay gặp khi chạy NestJS, Java, RabbitMQ, Kafka và Redis trên production. Mỗi sự cố ghi rõ triệu chứng nhìn thấy, nguyên nhân thường gặp, lệnh/công cụ để chẩn đoán, và cách xử lý cùng phòng ngừa.

__SECTIONS_incidents__ chủ đề__CODES_incidents__ đoạn lệnh/code

Quy trình khi có sự cố

  1. Giảm thiệt hại trướcRollback bản deploy gần nhất, tắt feature flag, scale thêm, chặn traffic xấu. Tìm nguyên nhân gốc sau.
  2. Thu thập bằng chứng trước khi restartRestart xóa mất trạng thái lỗi. Lấy heap dump / thread dump / log / metric trước nếu còn kịp.
  3. Khoanh vùngBắt đầu từ lúc nào? Trùng với deploy, thay đổi cấu hình, đợt traffic hay sự cố hạ tầng nào? Một instance hay tất cả?
  4. Đi theo đường đi của requestLoad balancer → app → DB/cache/broker → API ngoài. Thành phần nào có độ trễ hoặc tỉ lệ lỗi tăng đầu tiên?
  5. Sửa và xác nhậnXác nhận bằng metric (latency, error rate, lag) trở về bình thường, không chỉ bằng "hết thấy lỗi trong log".
  6. Postmortem không đổ lỗiDòng thời gian, nguyên nhân gốc, vì sao không phát hiện sớm, hành động phòng ngừa có người chịu trách nhiệm.
Bốn tín hiệu vàng

Mọi service nên có dashboard cho latency (p50/p95/p99), traffic, error rate, saturation (CPU, RAM, pool kết nối, độ dài queue, consumer lag). Hầu hết sự cố dưới đây lộ ra qua một trong bốn tín hiệu này trước khi người dùng phàn nàn.

NestJS / Node.js

Bộ nhớ tăng dần, pod bị OOMKilled rồi restart liên tục

Triệu chứng
RSS/heap tăng đều theo thời gian, không giảm sau GC; restart xong lại tăng. Log có JavaScript heap out of memory hoặc Kubernetes báo OOMKilled.
Nguyên nhân
Map/mảng dùng làm cache không giới hạn; listener (emitter.on, setInterval) đăng ký mỗi request mà không gỡ; closure giữ object lớn; query Mongo trả hàng chục nghìn document không lean(); buffer cả file upload vào RAM.
Chẩn đoán
node --heapsnapshot-signal=SIGUSR2 dist/main.js   # gửi kill -USR2  để chụp heap
node --heapsnapshot-near-heap-limit=2 dist/main.js # tự chụp tối đa 2 snapshot khi heap sắp đầy
# so sánh 2 snapshot cách nhau vài phút trong Chrome DevTools → Memory → Comparison
node --max-old-space-size=1536 dist/main.js       # đặt heap phù hợp limit container (~75%)
Chụp heap snapshot chặn event loop và có thể cần thêm bộ nhớ cỡ bằng heap: trong container sát limit, hãy rút pod khỏi load balancer trước khi chụp.
Xử lý
Cache có giới hạn (LRU + TTL, ví dụ lru-cache) hoặc chuyển sang Redis; gỡ listener trong onModuleDestroy; phân trang/stream khi đọc dữ liệu lớn; memoryStorage của Multer chỉ cho file nhỏ.

Latency tăng vọt, health check timeout dù CPU không cao lắm

Triệu chứng
Mọi endpoint chậm cùng lúc, kể cả /health; p99 nhảy lên hàng giây theo từng đợt.
Nguyên nhân
Event loop bị chặn: hàm đồng bộ nặng (bcrypt.hashSync, crypto.pbkdf2Sync, JSON.parse payload vài chục MB, vòng lặp lớn), regex backtracking thảm họa với input xấu, fs.readFileSync trong request.
Chẩn đoán
import { monitorEventLoopDelay } from 'node:perf_hooks';
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => { logger.log(`event loop p99=${(h.percentile(99) / 1e6).toFixed(0)}ms`); h.reset(); }, 10_000);
// tìm hàm nóng: node --cpu-prof dist/main.js rồi mở file .cpuprofile trong DevTools
Xử lý
Dùng API async (bcrypt.hash, argon2), đẩy việc CPU sang worker_threads hoặc queue; giới hạn kích thước body; viết lại regex hoặc giới hạn độ dài input; thêm metric event loop lag vào dashboard.

Process chết đột ngột vì unhandled rejection

Triệu chứng
Pod restart, log cuối là UnhandledPromiseRejection hoặc stack trace của một promise không ai await.
Nguyên nhân
Gọi hàm async "bắn rồi quên" (this.audit.log(x) không await, không catch); async callback trong forEach. Từ Node 15, chế độ mặc định là throw: rejection không xử lý làm sập process, trừ khi có listener process.on('unhandledRejection') (một số thư viện APM tự đăng ký, khiến hành vi khác nhau giữa môi trường).
Xử lý
Mọi lời gọi không await phải có .catch(): void this.audit.log(x).catch((e) => logger.warn(e)). Bật rule ESLint @typescript-eslint/no-floating-promises và no-misused-promises (cần cấu hình type-checked). Việc quan trọng thì đưa vào queue thay vì fire-and-forget.

Deploy xong ứng dụng không khởi động: "Nest can't resolve dependencies"

Triệu chứng
Local chạy được, bản build production crash ngay khi start; hoặc một provider nhận undefined.
Nguyên nhân
Circular import qua file barrel index.ts (thứ tự nạp module khác giữa tsc/SWC/bundle); quên export provider; biến môi trường thiếu làm factory ném lỗi.
Xử lý
Thêm bước CI khởi động app thật (smoke test gọi /health) trước khi deploy; bỏ barrel import trong cùng thư mục; validate env khi boot để lỗi rõ ràng; rollout từng phần (canary) để phát hiện sớm.

MongoDB chậm, request treo, lỗi "MongoServerSelectionError"/ pool timeout

Triệu chứng
Latency DB tăng, CPU Mongo cao, request xếp hàng chờ connection; có thể kèm lỗi WaitQueueTimeoutError (name: MongoWaitQueueTimeoutError) khi chờ connection quá waitQueueTimeoutMS. Kiểm tra bằng instanceof thay vì so chuỗi tên lỗi.
Nguyên nhân
Query thiếu index (COLLSCAN); $regex không có prefix; countDocuments trên collection lớn mỗi request; maxPoolSize quá nhỏ so với số request đồng thời, hoặc query chậm giữ connection lâu.
Chẩn đoán
db.setProfilingLevel(1, { slowms: 100 });              // ghi query chậm vào system.profile (không giữ sau restart)
db.system.profile.find().sort({ ts: -1 }).limit(10);
db.orders.find({ shop: 'demo', status: 'open' }).explain('executionStats');
// totalDocsExamined >> nReturned hoặc stage COLLSCAN → thiếu index
Xử lý
Index ghép theo quy tắc ESR: Equality → Sort → Range ($ne, $nin, $regex tính là range; range rất chọn lọc thì có thể đặt trước sort); lean() + projection; đặt maxTimeMS cho query; cache đếm tổng; tăng pool có cân nhắc (pool lớn không chữa được query chậm).

Mỗi lần deploy lại có 502 và mất message

Nguyên nhân
Pod nhận SIGTERM là chết ngay: request đang xử lý bị cắt, consumer bị đóng giữa chừng; load balancer vẫn gửi request tới pod đang tắt.
Xử lý
app.enableShutdownHooks() (tắt mặc định); Node phải nhận được SIGTERM: dùng exec form CMD ["node", "dist/main"] hoặc tini, không chạy qua npm start/sh -c; readiness probe trả 503 khi đang tắt; preStop: sleep 5; consumer dừng nhận message mới rồi đợi message đang xử lý trong onModuleDestroy; terminationGracePeriodSeconds đủ dài. Chi tiết ở pattern Graceful shutdown.

Request dồn ứ khi API bên ngoài chậm

Triệu chứng
Một nhà cung cấp (IP lookup, Shopify API) chậm làm toàn bộ service chậm theo, số kết nối mở tăng vọt.
Nguyên nhân
Gọi HTTP không đặt timeout; retry không giới hạn và không backoff; không có circuit breaker.
Xử lý
Timeout cho mọi lời gọi ra ngoài (connect + tổng); retry có backoff + jitter, chỉ cho thao tác idempotent; circuit breaker (ví dụ opossum); giới hạn concurrency tới từng upstream; có giá trị fallback (cache cũ, "unknown").

Gọi HTTP/DB chậm dù CPU thấp và event loop bình thường (libuv threadpool cạn)

Nguyên nhân
dns.lookup() (mọi client HTTP/DB/Redis dùng hostname) chạy getaddrinfo trên threadpool của libuv, mặc định chỉ 4 thread, dùng chung với fs, crypto.pbkdf2/scrypt, zlib. DNS chậm hoặc hash mật khẩu dồn dập làm mọi việc khác xếp hàng.
Chẩn đoán
Đo riêng thời gian phân giải DNS của request; xem có đợt hash/nén nặng trùng thời điểm.
Xử lý
Đặt UV_THREADPOOL_SIZE bằng biến môi trường trước khi process khởi động (đặt trong code không chắc có tác dụng); cache DNS; chuyển hash nặng sang worker thread.

502 lác đác sau load balancer, log app không có lỗi (lệch keep-alive)

Nguyên nhân
server.keepAliveTimeout của Node mặc định 5 giây, còn idle timeout của AWS ALB mặc định 60 giây: Node đóng socket rảnh đúng lúc ALB tái sử dụng nó. AWS khuyên keep-alive timeout của backend phải lớn hơn idle timeout của load balancer.
Chẩn đoán
Access log ALB có elb_status_code=502 với target_status_code=-.
Xử lý
const server = app.getHttpServer();
server.keepAliveTimeout = 65_000;   // > idle timeout của load balancer
server.headersTimeout = 66_000;     // lớn hơn keepAliveTimeout

"MaxListenersExceededWarning: Possible EventEmitter memory leak detected"

Nguyên nhân
Mỗi request gắn thêm listener vào object dùng chung (socket, Redis client, process) mà không gỡ; mặc định cảnh báo khi vượt 10 listener. Nhiều app gọi enableShutdownHooks trong cùng process cũng gây cảnh báo này.
Chẩn đoán
node --trace-warnings in stack của lần thêm listener vượt ngưỡng.
Xử lý
Dùng once, removeListener hoặc AbortSignal; chỉ tăng setMaxListeners khi số listener thật sự có giới hạn.

Bị OOMKilled trong khi heap V8 vẫn phẳng

Nguyên nhân
RSS gồm cả Buffer, external/arrayBuffers và addon native, nằm ngoài heap V8: buffer cả file upload/response lớn, nén dữ liệu trong RAM.
Chẩn đoán
process.memoryUsage(): so rss với heapTotal và external.
Xử lý
Stream thay vì buffer; giới hạn kích thước body; --max-old-space-size khoảng 75% limit để chừa chỗ cho phần ngoài heap.

Java / JVM

OutOfMemoryError: Java heap space

Triệu chứng
GC chạy liên tục, CPU cao, latency tăng rồi JVM ném OOM.
Nguyên nhân
Rò rỉ: static Map làm cache không giới hạn, listener không gỡ, ThreadLocal không remove() trong pool; hoặc tải dữ liệu quá lớn một lần (findAll() cả bảng).
Chẩn đoán
# luôn bật sẵn trên production
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps
jcmd  GC.class_histogram | head -30     # class nào chiếm nhiều nhất
jcmd  GC.heap_dump /dumps/now.hprof     # bắt buộc có tên file; mở bằng Eclipse MAT → Leak Suspects
Xử lý
Cache có giới hạn (Caffeine với maximumSize + expireAfterWrite); phân trang/stream dữ liệu lớn; ThreadLocal.remove() trong finally.

Container bị OOMKilled dù heap còn trống

Nguyên nhân
Bộ nhớ JVM = heap + metaspace + thread stack + direct buffer (Netty) + code cache + GC. Đặt -Xmx bằng đúng limit container thì phần ngoài heap làm vượt limit.
Chẩn đoán
java -XX:NativeMemoryTracking=summary ...
jcmd  VM.native_memory baseline         # chụp mốc
jcmd  VM.native_memory summary.diff     # sau một lúc: vùng nào tăng (Heap, Class, Thread, Internal…)
NMT tốn khoảng 5–10% hiệu năng và không thấy bộ nhớ malloc trực tiếp của thư viện native/JNI.
Xử lý
Dùng -XX:MaxRAMPercentage=75 thay vì -Xmx cứng; giới hạn -XX:MaxDirectMemorySize, -XX:MaxMetaspaceSize; giảm số thread platform (dùng virtual threads).

Ứng dụng "treo": request không trả về, CPU thấp

Nguyên nhân
Thread pool cạn: mọi thread đang chờ I/O không timeout, chờ connection DB, hoặc deadlock; task trong pool chờ task khác cùng pool.
Chẩn đoán
jcmd  Thread.print > dump1.txt; sleep 5; jcmd  Thread.print > dump2.txt
# thread nào đứng yên ở cùng frame qua 2 dump? cuối file có mục "Found one Java-level deadlock"
jcmd  Thread.dump_to_file -format=json /tmp/threads.json   # Thread.print không liệt kê virtual thread
Xử lý
Timeout cho mọi I/O và lần lấy lock (tryLock); tách pool cho từng loại việc (bulkhead); lấy lock theo thứ tự cố định; với I/O nhiều, chuyển sang virtual threads.

"Connection is not available, request timed out after 30001ms (total=10, active=10, idle=0, waiting=37)" (HikariCP)

Nguyên nhân
Rò rỉ connection (không đóng), transaction dài (gọi API ngoài bên trong @Transactional), pool quá nhỏ so với số thread, hoặc DB chậm.
Chẩn đoán
Phần (total, active, idle, waiting) trong thông báo lỗi cho biết pool đang cạn hay DB chậm. Metric Micrometer: hikaricp.connections.pending, .active, .acquire, .usage.
Xử lý
Bật leakDetectionThreshold (tối thiểu 2000ms) để log stack nơi mượn connection mà không trả; không gọi I/O ngoài trong transaction; maxLifetime ngắn hơn giới hạn của DB/hạ tầng vài giây. Wiki HikariCP khuyên pool nhỏ: công thức tham khảo connections = core_count × 2 + effective_spindle_count, mặc định maximumPoolSize = 10.

GC pause dài, latency p99 xấu

Chẩn đoán
-Xlog:gc*:file=gc.log:time,uptime, xem thời gian pause và tần suất Full GC; JFR để xem allocation rate theo method.
Xử lý
Heap quá nhỏ → tăng; tốc độ cấp phát quá cao → giảm tạo object tạm (stream lồng nhau, boxing, chuỗi lớn); cần pause rất ngắn → thử ZGC; tránh System.gc().

CPU 100% trên một core

Chẩn đoán
top -H -p                         # tìm thread id (TID) tốn CPU
printf '%x\n'                     # đổi sang hex
jcmd  Thread.print | grep -A 20 'nid=0x'
Nguyên nhân
Vòng lặp vô hạn, regex backtracking, retry không có delay, HashMap dùng chung không đồng bộ giữa các thread.

Thông lượng sụt sau khi chuyển sang virtual threads

Nguyên nhân
JDK 21–23: blocking bên trong synchronized làm virtual thread bị ghim vào carrier; thư viện cũ (driver JDBC) dùng synchronized nhiều. Hoặc pool tài nguyên (DB) nhỏ trong khi số virtual thread không giới hạn.
Xử lý
Nâng JDK 24+ (JEP 491: synchronized không còn ghim; vẫn ghim khi có frame native/foreign function hoặc trong class initializer); kiểm tra JFR event jdk.VirtualThreadPinned; giới hạn đồng thời bằng Semaphore trước tài nguyên khan hiếm.

"java.net.SocketException: Too many open files"

Nguyên nhân
Không đóng stream/socket/response; tạo HTTP client mới mỗi request; ulimit -n quá thấp.
Chẩn đoán
ls /proc/<pid>/fd | wc -l, lsof -p <pid> để xem loại file/socket đang mở nhiều; metric JMX OpenFileDescriptorCount.
Xử lý
try-with-resources, dùng chung client; nâng giới hạn nofile khi số kết nối hợp lệ thật sự lớn.

OutOfMemoryError: Metaspace sau nhiều lần redeploy

Nguyên nhân
Classloader cũ không được giải phóng (ThreadLocal, static cache, driver JDBC đăng ký toàn cục giữ tham chiếu), hoặc sinh class động liên tục (proxy, script).
Chẩn đoán
jcmd <pid> VM.classloader_stats; vùng Class tăng trong VM.native_memory summary.diff.
Xử lý
Tìm thứ giữ classloader; cache proxy đã sinh; đặt -XX:MaxMetaspaceSize để lỗi lộ ra sớm thay vì ăn hết RAM.

"GC overhead limit exceeded"

Nguyên nhân
JVM dành hơn ~98% thời gian cho GC mà thu hồi được dưới 2% heap qua nhiều lần liên tiếp: heap gần đầy vì rò rỉ hoặc quá nhỏ.
Xử lý
Như OOM heap: so 2 lần GC.class_histogram, heap dump, sửa rò rỉ hoặc tăng heap. Tắt bằng -XX:-UseGCOverheadLimit chỉ che giấu vấn đề.

Sau failover DB/cache, ứng dụng vẫn kết nối IP cũ

Nguyên nhân
JVM cache kết quả DNS (networkaddress.cache.ttl; -1 là cache vĩnh viễn, thường gặp khi bật security manager hoặc cấu hình cũ) và pool giữ connection cũ.
Xử lý
Đặt TTL rõ ràng (ví dụ 30–60 giây) trong java.security hoặc Security.setProperty("networkaddress.cache.ttl", "60") lúc khởi động; maxLifetime của pool để connection được làm mới.

CompletableFuture và parallelStream cùng "đứng hình" khi tải cao

Nguyên nhân
Mọi method async của CompletableFuture không truyền executor đều chạy trên ForkJoinPool.commonPool() (khoảng số core − 1 thread). Đặt I/O blocking vào supplyAsync làm cạn pool dùng chung của cả JVM.
Chẩn đoán
Thread dump: mọi ForkJoinPool.commonPool-worker-* đều đang chờ đọc socket.
Xử lý
Luôn truyền executor riêng cho I/O (pool có giới hạn hoặc newVirtualThreadPerTaskExecutor()).

Thời gian âm, JWT "used before issued" sau khi đồng bộ giờ

Nguyên nhân
Đo khoảng thời gian bằng System.currentTimeMillis() (đồng hồ thực, có thể nhảy khi NTP chỉnh); lệch giờ giữa các máy.
Xử lý
System.nanoTime() cho đo thời gian trôi qua; cho phép sai lệch giờ vài chục giây khi kiểm tra JWT; chạy chrony/NTP.

RabbitMQ

Queue tồn đọng tăng mãi

Triệu chứng
Số message "Ready" tăng liên tục; xử lý nghiệp vụ bị trễ hàng giờ.
Chẩn đoán
rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers
# consumers = 0 → consumer chết/mất kết nối; unacked cao + ready cao → consumer chậm hoặc kẹt
Xử lý
Khôi phục consumer; scale ngang; tìm bước chậm (API ngoài, DB); tối ưu prefetch; cảnh báo theo độ dài queue và tuổi message cũ nhất; đặt max-length để bảo vệ broker.

Publisher bị treo: memory/disk alarm

Triệu chứng
Lệnh publish không trả về; UI báo connection ở trạng thái blocked/blocking; log broker có memory resource limit alarm set hoặc disk resource limit alarm.
Nguyên nhân
Broker chạm vm_memory_high_watermark hoặc disk_free_limit, thường do tồn đọng lớn hoặc message quá to.
Lưu ý
Alarm có hiệu lực toàn cụm; broker ngừng đọc socket của publisher (connection.blocked chỉ là thông báo cho client đăng ký nhận). Connection chỉ consume không bị chặn, nên tách connection publish và consume để consumer vẫn xả được tồn đọng.
Xử lý
Xả tồn đọng (thêm consumer, purge queue rác), thêm đĩa/RAM; về lâu dài: max-length cho queue, dùng stream cho khối lượng lớn, không gửi payload lớn qua broker (lưu S3, gửi link). Ở client, lắng nghe sự kiện blocked để báo động thay vì treo im lặng.

Poison message quay vòng vô hạn

Triệu chứng
CPU consumer cao, cùng một lỗi lặp lại liên tục trong log, message có cờ redelivered=true; queue không giảm.
Nguyên nhân
Consumer nack(requeue=true) cho lỗi vĩnh viễn (JSON sai, dữ liệu không hợp lệ).
Xử lý
Quorum queue với delivery-limit + DLX; phân loại lỗi tạm thời và vĩnh viễn; retry có độ trễ; parking lot queue cho người xem xét. Xem pattern Retry có độ trễ.

Consumer bị ngắt: "delivery acknowledgement … timed out"

Triệu chứng
≤ 4.2: channel bị đóng với PRECONDITION_FAILED - delivery acknowledgement on channel N timed out, message chưa ack được giao lại. Từ 4.3: consumer bị hủy (client hỗ trợ consumer cancel notification sẽ nhận thông báo).
Nguyên nhân
Consumer giữ message chưa ack quá consumer timeout (mặc định 30 phút, broker kiểm tra khoảng mỗi phút): job quá dài, hoặc có nhánh code quên ack/nack.
Xử lý
Mọi nhánh đều ack hoặc nack (try/finally); việc rất dài thì ack sớm và theo dõi trạng thái trong DB, hoặc chia nhỏ. Cần thời gian dài hơn thì đặt riêng cho queue bằng policy consumer-timeout / x-consumer-timeout (từ 3.12; 4.3 thêm theo từng consumer). Không đặt dưới 1 phút.

Mất message

Nguyên nhân
Một trong các mắt xích thiếu: không publisher confirm; message không persistent; queue không durable/classic không replicate khi node chết; auto-ack; routing key không khớp binding nào nên message bị bỏ im lặng; DLX chưa tồn tại lúc dead-letter.
Xử lý
Quorum queue + persistent + confirm + manual ack; publish với mandatory hoặc alternate exchange để bắt message không định tuyến được; khai báo topology (exchange, DLX) lúc khởi động.

Ứng dụng không khởi động: "PRECONDITION_FAILED - inequivalent arg"

Nguyên nhân
Code mới khai báo lại queue với x-arguments khác queue đang tồn tại (thêm DLX, đổi sang quorum).
Xử lý
Tham số đổi được thì chuyển sang policy; đổi loại queue thì tạo queue mới (orders.v2), bind song song, chuyển consumer, xả queue cũ rồi xóa.

Quá nhiều connection/channel, broker hết file descriptor

Nguyên nhân
Mở connection mới cho mỗi lần publish; channel không đóng; autoscale tạo hàng trăm pod mỗi pod nhiều connection.
Xử lý
Một connection dùng lâu dài mỗi process (tách publish/consume), pool channel; giới hạn bằng rabbitmqctl set_vhost_limits; theo dõi tốc độ mở/đóng connection (churn).

Message biến mất, không có trong DLQ (quorum queue 4.x)

Nguyên nhân
Quorum queue có delivery-limit mặc định 20 từ 4.0; vượt ngưỡng mà queue không có DLX thì message bị bỏ.
Chẩn đoán
Xem policy hiệu lực của queue; header x-delivery-count trên message.
Xử lý
Luôn đặt DLX bằng policy và delivery-limit tường minh. Từ 4.3, nack có requeue không làm tăng bộ đếm, chỉ lần giao thất bại mới tính.

Sau khi nâng lên 4.3, consumer kẹt trên classic queue không bao giờ bị ngắt

Nguyên nhân
4.3 bỏ việc kiểm tra consumer timeout cho classic queue: message chưa ack nằm mãi.
Xử lý
Chuyển sang quorum queue, hoặc thêm watchdog ở ứng dụng (giới hạn thời gian xử lý mỗi message).

Kết nối rớt ngẫu nhiên sau load balancer (missed heartbeats)

Nguyên nhân
Idle timeout của load balancer/NAT ngắn hơn heartbeat; hoặc tắt heartbeat nên peer chết không bị phát hiện (Linux mất khoảng 11 phút mới nhận ra).
Chẩn đoán
Log broker báo đóng kết nối vì missed heartbeats; rabbitmqctl list_connections name timeout state.
Xử lý
Heartbeat 5–20 giây (mặc định server 60 giây; dưới 5 giây dễ báo nhầm); idle timeout của load balancer lớn hơn khoảng heartbeat.

Thông lượng publish tụt, connection ở trạng thái "flow"

Nguyên nhân
Credit flow (back-pressure nội bộ): queue không theo kịp tốc độ nhận vì ghi đĩa, replication, consumer chậm hoặc prefetch thấp.
Chẩn đoán
rabbitmqctl list_connections name state hiện flow; UI quản trị cũng hiển thị; xem consumer_utilisation của queue.
Xử lý
Thêm consumer hoặc tăng prefetch, chia tải ra nhiều queue, đĩa nhanh hơn.

Node không join được cluster

Triệu chứng
Authentication failed (rejected by the remote node), please check the Erlang cookie.
Nguyên nhân
Erlang cookie khác nhau; lệch short/long hostname; hostname thay đổi (node khởi động như node mới, trống).
Xử lý
Cùng cookie mọi node (rabbitmq-diagnostics erlang_cookie_sources); RABBITMQ_USE_LONGNAME nhất quán; hostname ổn định (StatefulSet trên Kubernetes).

Đĩa đầy vì quorum queue

Nguyên nhân
Segment chỉ được dọn khi message được ack; queue dài hoặc message treo chưa ack giữ log lại (trước 4.3, một message treo lâu có thể chặn việc cắt log). WAL dùng chung mặc định 512MiB.
Xử lý
Giữ queue ngắn, dư dả đĩa, RAM node ≥ 3–4 lần giới hạn WAL; nâng lên 4.3+.

Consumer lag tăng liên tục

Chẩn đoán

# LAG lệch ở vài partition → key nóng hoặc consumer của partition đó chậm
# LAG đều mọi partition → consumer tổng thể không theo kịp
Nguyên nhân
Xử lý từng record chậm (gọi API/DB tuần tự); số consumer đã bằng số partition; rebalance liên tục; key nóng dồn vào một partition.
Xử lý
Xử lý theo batch, song song bên trong partition theo key (giữ thứ tự từng key); tăng partition (chú ý ánh xạ key thay đổi); tách việc chậm sang topic/queue khác; cảnh báo theo lag và theo "thời gian trễ" ước tính.

Rebalance liên tục ("rebalance storm")

Triệu chứng
Log lặp lại Attempt to heartbeat failed since group is rebalancing, consumer poll timeout has expired; thông lượng gần như bằng 0.
Nguyên nhân
Xử lý một batch lâu hơn max.poll.interval.ms (mặc định 5 phút; log: sending LeaveGroup request … due to consumer poll timeout has expired) nên consumer bị đá khỏi group, partition chuyển đi, lại xử lý lại; deploy rolling làm group rebalance nhiều lần.
Xử lý
Giảm max.poll.records, tăng max.poll.interval.ms cho việc nặng; static membership (group.instance.id); dùng giao thức mới group.protocol=consumer (Kafka 4.0+) để rebalance tăng dần, ít gián đoạn.

Poison pill làm kẹt cả partition

Triệu chứng
Lag của một partition đứng yên, log lặp SerializationException hoặc lỗi xử lý ở cùng một offset.
Xử lý
Bắt lỗi deserialize (Spring: ErrorHandlingDeserializer), gửi record lỗi sang DLT rồi commit để đi tiếp. Khẩn cấp có thể nhảy qua offset khi mọi consumer của group đã dừng (công cụ từ chối nếu group còn thành viên; mặc định chỉ dry-run): 
kafka-consumer-groups.sh --bootstrap-server $B --group risk \
  --topic orders.created:3 --reset-offsets --shift-by 1 --execute

Xử lý trùng sau khi restart hoặc rebalance

Nguyên nhân
At-least-once là mặc định: xử lý xong nhưng chưa kịp commit thì consumer chết, consumer mới đọc lại từ offset cũ.
Xử lý
Consumer idempotent (bảng processed với unique key, upsert theo khóa nghiệp vụ); commit thường xuyên hơn; Kafka → Kafka thì dùng transaction/exactly-once.

Mất dữ liệu: consumer bỏ qua message

Nguyên nhân
auto.offset.reset=latest (mặc định) với group mới, partition mới thêm, hoặc offset đã hết hạn (offsets.retention.minutes = 7 ngày, tính từ lúc group không còn thành viên) nên consumer nhảy về cuối; lag lớn hơn retention nên dữ liệu bị xóa trước khi đọc; acks=1 và leader chết trước khi replica sao chép.
Xử lý
auto.offset.reset=earliest cho group quan trọng; cảnh báo khi lag tiến gần retention; acks=all + min.insync.replicas=2 + RF 3; giữ unclean.leader.election.enable=false.

Producer báo NotEnoughReplicas / timeout khi một broker chết

Nguyên nhân
RF=2 với min.insync.replicas=2: chỉ cần một broker chết là không ghi được. Hoặc broker quá tải khiến ISR co lại.
Xử lý
RF=3, min.insync=2 (chịu được mất một broker); theo dõi metric under-replicated partitions; producer có delivery.timeout.ms hợp lý và xử lý callback lỗi.

Broker đầy đĩa

Xử lý
Khẩn cấp: giảm retention.ms của topic lớn nhất (kafka-configs.sh --alter --add-config retention.ms=...), Kafka xóa segment cũ trong vài phút. Lâu dài: tính dung lượng = thông lượng × retention × RF, cảnh báo ở 70%, bật nén (zstd), xem xét tiered storage.

ISR co lại, producer acks=all báo NotEnoughReplicas

Nguyên nhân
Broker chậm/chết, đĩa hoặc mạng bão hòa: follower bị loại khỏi ISR sau replica.lag.time.max.ms (30 giây), ISR xuống dưới min.insync.replicas.
Chẩn đoán
Metric IsrShrinksPerSec, UnderReplicatedPartitions, UnderMinIsrPartitionCount.
Xử lý
Khôi phục broker, kiểm tra đĩa; không bật unclean.leader.election.enable trừ khi chấp nhận mất dữ liệu.

Một broker quá tải sau khi restart (leader lệch)

Nguyên nhân
Leadership chưa chuyển về preferred replica sau khi broker quay lại.
Xử lý

# dữ liệu lệch thật sự: kafka-reassign-partitions.sh --generate / --execute / --verify
Kiểm tra auto.leader.rebalance.enable (mặc định bật).

Nguyên nhân

Redis

Latency Redis tăng đột biến

Chẩn đoán
redis-cli SLOWLOG GET 20                          # lệnh chậm (mặc định ghi lệnh > 10ms, chỉ tính thời gian thực thi)
redis-cli CONFIG SET latency-monitor-threshold 100  # latency monitor tắt mặc định
redis-cli LATENCY DOCTOR                          # phân tích các sự kiện: command, fork, aof, expire-cycle…

Xử lý
Tìm prefix chiếm nhiều bộ nhớ (--bigkeys, MEMORY USAGE key, phân tích RDB); thêm TTL; MAXLEN cho stream; removeOnComplete cho BullMQ; instance cache dùng allkeys-lru.

Job/khóa biến mất bí ẩn

Nguyên nhân
Queue/khóa nằm chung instance với cache dùng allkeys-lru: khi đầy, Redis xóa luôn key của queue.
Xử lý
Tách instance: cache (allkeys-lru) và dữ liệu cần bền (noeviction + persistence); theo dõi evicted_keys trong INFO stats.

Database quá tải sau khi Redis restart / flush (cache stampede)

Xử lý

"ERR max number of clients reached"

Xử lý

Hai worker cùng chạy một job dù đã có khóa

Nguyên nhân
Job chạy lâu hơn TTL của khóa nên khóa hết hạn, worker khác lấy được; giải phóng khóa bằng DEL thẳng (xóa luôn khóa của người khác).
Xử lý
TTL dài hơn thời gian chạy tối đa hoặc gia hạn định kỳ (watchdog như Redisson); giải phóng có kiểm tra token: Lua get-compare-del, hoặc từ Redis 8.4 dùng DELEX key IFEQ token. Docs Redis lưu ý TTL dựa trên đồng hồ hệ thống (không monotonic) nên đồng hồ nhảy cũng có thể sinh hai người giữ khóa: khi cần đúng tuyệt đối, dùng fencing token kiểm tra ở tài nguyên đích hoặc ràng buộc DB (unique, version).
