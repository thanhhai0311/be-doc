Redis là gì

Redis lưu dữ liệu trong RAM với cấu trúc dữ liệu phong phú (không chỉ key-value chuỗi), nên mỗi thao tác thường chỉ tốn micro-giây. Lệnh được thực thi tuần tự trên một luồng chính, nên từng lệnh là nguyên tử.

  • Redis 8 gộp các tính năng trước đây là module (JSON, Query Engine/Search, time series, kiểu xác suất như Bloom, Top-K, t-digest) và thêm vector set. Từ 8.0, Redis Open Source có thêm lựa chọn giấy phép AGPLv3.
  • Valkey là bản fork mã nguồn mở (giấy phép BSD) do Linux Foundation duy trì, tương thích giao thức với Redis 7.2; client như ioredis, Lettuce dùng được cho cả hai.
docker run -d --name redis -p 6379:6379 redis:8
redis-cli ping                 # PONG
redis-cli --latency            # đo độ trễ
redis-cli INFO memory

Pub/Sub và Streams

Pub/Sub: PUBLISH channel msg gửi tới mọi client đang SUBSCRIBE; client offline là mất. Hợp với tín hiệu tức thời như xóa cache cục bộ trên mọi instance. Trên cluster dùng sharded pub/sub (SPUBLISH/SSUBSCRIBE).

Streams: log bền có consumer group, giống Kafka thu nhỏ trong Redis.

XGROUP CREATE visits writers $ MKSTREAM                    # tạo group, đọc từ message mới
XADD visits MAXLEN ~ 1000000 * shop demo ip 1.2.3.4         # ~ = cắt gần đúng, nhanh hơn
XREADGROUP GROUP writers c1 COUNT 100 BLOCK 5000 STREAMS visits >   # > = message chưa giao cho ai
XACK visits writers 1731722400000-0
XPENDING visits writers                                     # message đã giao mà chưa ack
XAUTOCLAIM visits writers c2 60000 0-0 COUNT 100            # lấy lại message treo quá 60s

Tách vai trò

Không trộn cache (cho phép mất) với queue/khóa (không được mất) trên cùng instance với allkeys-lru: Redis có thể xóa mất job của BullMQ. Dùng hai instance hoặc noeviction cho instance chứa queue.

Replication, Sentinel và Cluster

  • Replication: replica sao chép bất đồng bộ từ master; đọc được từ replica (có thể hơi cũ). WAIT chờ N replica nhận ghi.
  • Sentinel: giám sát master, tự failover sang replica, cho client biết master mới. Hợp khi dữ liệu vừa một máy.
  • Cluster: chia dữ liệu theo 16384 hash slot (CRC16(key) mod 16384) trên nhiều master, tối thiểu 3 master (khuyên 3 master + 3 replica).

Lệnh nhiều key (MGET, MULTI, Lua) trên cluster chỉ chạy khi mọi key cùng slot, nếu không sẽ lỗi CROSSSLOT. Dùng hash tag: chỉ phần trong {'{'}…{'}'} được băm.

SET rl:{shop-1}:minute 1
SET rl:{shop-1}:hour 1          # cùng slot với key trên nhờ {shop-1}

import Redis from 'ioredis';

export const REDIS = Symbol('REDIS');

@Global()
@Module({
  providers: [{
    provide: REDIS,
    inject: [ConfigService],
    useFactory: (c: ConfigService) => {
      const client = new Redis(c.getOrThrow('REDIS_URL'), {
        maxRetriesPerRequest: 3,
        enableAutoPipelining: true,             // tự gom lệnh cùng vòng event loop
      });
      client.on('error', (e) => Logger.error(e.message, 'Redis'));  // thiếu listener → crash khi mất kết nối
      return client;
    },
  }],
  exports: [REDIS],
})
export class RedisModule implements OnApplicationShutdown {
  constructor(@Inject(REDIS) private readonly redis: Redis) {}
  async onApplicationShutdown() { await this.redis.quit(); }
}

@Injectable()
export class VisitCounter {
  constructor(@Inject(REDIS) private readonly redis: Redis) {}

  async hit(shop: string) {
    const day = new Date().toISOString().slice(0, 10);
    const [[, count]] = (await this.redis.multi()
      .incr(`visits:${shop}:${day}`)
      .expire(`visits:${shop}:${day}`, 2 * 86_400)
      .exec())!;
    return count as number;
  }
}

Cache-aside và chống cache stampede

Đọc cache trước; miss thì đọc DB rồi ghi cache với TTL; khi ghi dữ liệu thì xóa cache. Ba vấn đề cần xử lý:

  • Stampede: key nóng hết hạn, hàng trăm request cùng lúc đánh vào DB. Chỉ cho một request tính lại (khóa ngắn hoặc single-flight trong process).
  • Hết hạn đồng loạt: thêm jitter ngẫu nhiên vào TTL.
  • Penetration: truy vấn key không tồn tại liên tục đi thẳng vào DB. Cache cả kết quả "không có" với TTL ngắn, hoặc dùng Bloom filter.
@Injectable()
export class CacheAside {
  private readonly inflight = new Map>();   // single-flight trong process
  constructor(@Inject(REDIS) private readonly redis: Redis) {}

  async get(key: string, ttlSec: number, load: () => Promise): Promise {
    const hit = await this.redis.get(key);
    if (hit !== null) return hit === '__null__' ? null : (JSON.parse(hit) as T);

    const running = this.inflight.get(key);
    if (running) return running as Promise;

    const p = (async () => {
      const value = await load();
      const ttl = value === null ? 30 : ttlSec + Math.floor(Math.random() * ttlSec * 0.1);  // jitter 10%
      await this.redis.set(key, value === null ? '__null__' : JSON.stringify(value), 'EX', ttl);
      return value;
    })().finally(() => this.inflight.delete(key));

    this.inflight.set(key, p);
    return p;
  }

  invalidate(key: string) { return this.redis.unlink(key); }
}

Nhiều instance cùng giữ cache cục bộ (L1) thì publish sự kiện xóa qua Pub/Sub để mọi instance xóa bản trong RAM.

Distributed lock

SET key token NX PX ttl để lấy khóa; giải phóng bằng Lua kiểm tra token (chỉ chủ khóa mới xóa được). Ví dụ đầy đủ cho Nest ở tab NestJS, cho Java ở mục Redisson phía trên.

-- release.lua: KEYS[1] = lock key, ARGV[1] = token
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
Giới hạn

Khóa trên một Redis không an toàn tuyệt đối: master sập trước khi replica nhận key, hoặc tiến trình bị dừng (GC pause) quá TTL, đều có thể khiến hai nơi cùng giữ khóa. Redlock (nhiều node độc lập) giảm rủi ro nhưng vẫn còn tranh luận. Khi đúng đắn là bắt buộc (trừ tiền), thêm fencing token (số tăng dần kiểm tra ở DB) hoặc dùng ràng buộc unique/transaction của DB.

// fixed window
async allowFixed(ip: string, limit = 100) {
  const key = `rl:${ip}:${Math.floor(Date.now() / 60_000)}`;
  const [[, count]] = (await this.redis.multi().incr(key).expire(key, 120).exec())!;
  return (count as number) <= limit;
}

// sliding window: chạy nguyên tử bằng Lua
const SLIDING = `
local key, now, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
if redis.call('ZCARD', key) >= limit then return 0 end
redis.call('ZADD', key, now, ARGV[4])
redis.call('PEXPIRE', key, window)
return 1`;

this.redis.defineCommand('slidingLimit', { numberOfKeys: 1, lua: SLIDING });

async allowSliding(ip: string) {
  const ok = await (this.redis as any).slidingLimit(`rl:sw:${ip}`, Date.now(), 60_000, 100, randomUUID());
  return ok === 1;
}

Hàng đợi tin cậy với Streams

@Injectable()
export class VisitStreamWorker implements OnModuleInit, OnModuleDestroy {
  private running = true;
  private readonly name = `worker-${process.pid}`;
  constructor(@Inject(REDIS) private readonly redis: Redis) {}

  async onModuleInit() {
    await this.redis.xgroup('CREATE', 'visits', 'writers', '$', 'MKSTREAM').catch((e) => {
      if (!String(e).includes('BUSYGROUP')) throw e;           // group đã tồn tại
    });
    void this.loop();
  }

  onModuleDestroy() { this.running = false; }

  private async loop() {
    const reader = this.redis.duplicate();                      // lệnh BLOCK cần connection riêng
    while (this.running) {
      const res = (await reader.xreadgroup('GROUP', 'writers', this.name,
        'COUNT', 100, 'BLOCK', 5000, 'STREAMS', 'visits', '>')) as [string, [string, string[]][]][] | null;
      if (!res) continue;
      for (const [, entries] of res) {
        for (const [id, fields] of entries) {
          await this.handle(fields);
          await this.redis.xack('visits', 'writers', id);
        }
      }
    }
    await reader.quit();
  }
}

// producer
await redis.xadd('visits', 'MAXLEN', '~', 1_000_000, '*', 'shop', shop, 'ip', ip);

Định kỳ chạy XAUTOCLAIM để nhận lại message của worker đã chết; message có số lần giao (XPENDING) quá ngưỡng thì chuyển sang stream dead-letter. Cần nhiều tính năng (retry, delay, priority, UI) thì dùng BullMQ (Nest) hoặc Redisson RReliableQueue/RabbitMQ.

Session, idempotency key, feature flag

  • Session: hash sess:<id> với TTL trượt (gia hạn mỗi request). Spring Session và connect-redis (Express) làm sẵn.
  • Idempotency key: SET idem:<key> PENDING NX EX 86400 → xử lý → ghi kết quả. Ví dụ đầy đủ ở tab NestJS.
  • Feature flag / cấu hình nóng: hash flags, cache cục bộ vài giây, Pub/Sub để báo thay đổi.
  • Deduplicate sự kiện: SET seen:<eventId> 1 NX EX 604800; trả về null nghĩa là đã xử lý.

Checklist production

  • Đặt maxmemory và policy phù hợp vai trò (cache: allkeys-lru/lfu; queue/khóa: noeviction), chừa RAM cho fork và buffer.
  • Cache luôn có TTL; key có quy ước đặt tên và prefix theo ứng dụng.
  • Không KEYS, không big key; theo dõi SLOWLOG, INFO, tỉ lệ hit, số client kết nối.
  • HA bằng Sentinel hoặc Cluster; client cấu hình đúng chế độ; hash tag cho thao tác nhiều key.
  • Bật ACL (user riêng cho mỗi ứng dụng), TLS, không mở cổng 6379 ra Internet.
  • Client: một connection dùng lâu dài, có listener lỗi, timeout và giới hạn retry.
  • Persistence: AOF everysec nếu dữ liệu quan trọng; sao lưu RDB định kỳ ra ngoài máy.
