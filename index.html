Bắt đầu

NestJS là gì

NestJS là framework Node.js để viết ứng dụng phía server bằng TypeScript. Nest không tự xử lý HTTP mà chạy trên một HTTP adapter: mặc định là Express, có thể đổi sang Fastify (từ v12.3 có thêm Node adapter dùng thẳng node:http). Phần Nest thêm vào là kiến trúc: chia ứng dụng thành module, quản lý phụ thuộc bằng Dependency Injection (DI), và khai báo hành vi bằng decorator.

Ba ý tưởng cốt lõi cần nắm trước khi đọc tiếp:

  • Module gom các class liên quan thành một khối có ranh giới rõ ràng. Mọi ứng dụng có ít nhất một root module (AppModule).
  • Provider + DI: class đánh dấu @Injectable() được Nest tạo instance và "tiêm" vào constructor của class khác. Bạn không tự gọi new.
  • Decorator + metadata: @Controller, @Get, @UseGuards… gắn metadata lên class/method, Nest đọc metadata đó lúc khởi động để dựng route và pipeline xử lý request.

File main.ts

NestFactory.create() đọc root module, dựng toàn bộ cây DI, đăng ký route rồi trả về instance ứng dụng. Mọi cấu hình toàn cục (prefix, CORS, pipe global…) đặt ở đây.

src/main.ts
import { NestFactory } from '@nestjs/core';
import { ValidationPipe, VersioningType } from '@nestjs/common';
import { NestExpressApplication } from '@nestjs/platform-express';
import { AppModule } from './app.module';

async function bootstrap() {
  const app = await NestFactory.create<NestExpressApplication>(AppModule, {
    bufferLogs: true,     // giữ log khởi động cho tới khi gắn logger tùy chỉnh
    rawBody: true,        // cần khi verify chữ ký webhook (Shopify, Stripe…)
  });

  app.setGlobalPrefix('api');                     // mọi route bắt đầu bằng /api
  app.enableVersioning({ type: VersioningType.URI }); // /api/v1/...
  app.enableCors({ origin: ['https://admin.example.com'], credentials: true });
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
  app.enableShutdownHooks();                      // để onModuleDestroy chạy khi nhận SIGTERM

  await app.listen(process.env.PORT ?? 3000);
}
bootstrap();

Kiến trúc và vòng đời request

Nest có tám loại "viên gạch". Hiểu mỗi loại làm gì và chạy ở đâu trong vòng đời request là phần quan trọng nhất của framework.

Thành phầnInterface / decoratorTrách nhiệm
Module@Module()Gom và đóng gói controller, provider; khai báo phụ thuộc giữa các phần.
Controller@Controller()Nhận request, gọi service, trả response. Không chứa business logic.
Provider@Injectable()Service, repository, factory, helper… mọi thứ được DI quản lý.
MiddlewareNestMiddlewareChạy trước khi Nest biết route nào sẽ xử lý. Hợp với log thô, gắn request-id, parse body.
GuardCanActivateQuyết định request có được đi tiếp hay không (xác thực, phân quyền).
InterceptorNestInterceptorBọc quanh handler: chạy logic trước và sau, biến đổi kết quả, cache, timeout.
PipePipeTransformValidate và chuyển đổi tham số đầu vào của handler.
Exception filterExceptionFilterBắt exception chưa được xử lý và định dạng response lỗi.

Thứ tự xử lý một request

Thứ tự dưới đây lấy từ trang FAQ "Request lifecycle" của docs chính thức.

  1. Request đếnAdapter (Express/Fastify) nhận HTTP request.
  2. MiddlewareMiddleware global (app.use) → middleware gắn theo module. Module @Global() chạy trước, root module, rồi các module khác theo khoảng cách tới root.
  3. GuardsGlobal → controller → route. Guard nào trả false thì dừng với 403.
  4. Interceptors (trước handler)Global → controller → route.
  5. PipesGlobal → controller → route → pipe gắn trên từng tham số (tham số cuối chạy trước).
  6. Controller handlerMethod gắn @Get/@Post… được gọi.
  7. ServiceBusiness logic, gọi DB, gọi API ngoài.
  8. Interceptors (sau handler)Chiều ngược lại: route → controller → global.
  9. Exception filtersChỉ chạy khi có exception chưa bắt. Route → controller → global, và chỉ một filter xử lý (không chạy nối tiếp).
  10. ResponseAdapter gửi kết quả về client.

Tương tự có APP_INTERCEPTOR, APP_PIPE, APP_FILTER (import từ @nestjs/core). Truyền class thay vì instance để Nest tự tạo và inject phụ thuộc.

src/app.module.ts
import { Module } from '@nestjs/common';
import { APP_FILTER, APP_GUARD, APP_INTERCEPTOR } from '@nestjs/core';

@Module({
  providers: [
    { provide: APP_GUARD, useClass: AuthGuard },            // chạy trước
    { provide: APP_GUARD, useClass: RolesGuard },           // chạy sau (theo thứ tự đăng ký)
    { provide: APP_INTERCEPTOR, useClass: ResponseInterceptor },
    { provide: APP_FILTER, useClass: AllExceptionsFilter },
  ],
})
export class AppModule {}

Controllers

Controller nhận request và trả response. Decorator @Controller('cats') đặt prefix đường dẫn; decorator HTTP method trên từng method khai báo route con.

src/cats/cats.controller.ts
import {
  Body, Controller, Delete, Get, HttpCode, HttpStatus, Param,
  ParseIntPipe, Patch, Post, Query, Header, Redirect,
} from '@nestjs/common';
import { CatsService } from './cats.service';
import { CreateCatDto, UpdateCatDto, ListCatsQuery } from './dto';

@Controller('cats')                         // prefix: /cats
export class CatsController {
  constructor(private readonly catsService: CatsService) {}

  @Post()                                   // POST /cats  → mặc định 201
  create(@Body() dto: CreateCatDto) {
    return this.catsService.create(dto);
  }

  @Get()                                    // GET /cats?page=1&limit=20
  findAll(@Query() query: ListCatsQuery) {
    return this.catsService.findAll(query);
  }

  @Get(':id')                               // GET /cats/42
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.catsService.findOne(id);
  }

  @Patch(':id')
  update(@Param('id', ParseIntPipe) id: number, @Body() dto: UpdateCatDto) {
    return this.catsService.update(id, dto);
  }

  @Delete(':id')
  @HttpCode(HttpStatus.NO_CONTENT)          // đổi status mặc định 200 → 204
  remove(@Param('id', ParseIntPipe) id: number) {
    return this.catsService.remove(id);
  }

  @Get('docs')
  @Redirect('https://docs.nestjs.com', 302)
  docs() {}

  @Get('export.csv')
  @Header('Content-Type', 'text/csv')
  exportCsv() {
    return 'id,name\n1,Tom';
  }
}

Controller phải được khai báo trong mảng controllers của một module thì Nest mới đăng ký route.

Giá trị trả về và @Res()

Handler có thể trả về giá trị thường, Promise hoặc Observable. Nest tự serialize object/array thành JSON. Status mặc định là 200, riêng POST là 201.

Khi inject @Res(), bạn chuyển sang chế độ "tự quản response": Nest không gửi response giùm nữa, interceptor và @HttpCode không còn tác dụng. Nếu chỉ cần set cookie hay header, dùng passthrough:

@Get()
findAll(@Res({ passthrough: true }) res: Response) {
  res.setHeader('X-Total-Count', '120');
  return this.catsService.findAll();   // Nest vẫn gửi body như bình thường
}

Thứ tự route và wildcard

  • Route được đăng ký theo thứ tự khai báo. Nếu @Get(':id') đứng trước @Get('me'), request /users/me sẽ rơi vào :id. Luôn đặt route tĩnh lên trước route có tham số.
  • Express 5 (Nest 11+) bắt buộc wildcard có tên: dùng 'files/*path' hoặc 'files/{*path}' (dạng có ngoặc nhọn khớp cả /files). Dạng '*' trần đã deprecated.
  • Sub-domain: @Controller({ host: ':account.example.com' }) rồi đọc bằng @HostParam('account') (không hỗ trợ trên Fastify).

Providers và Dependency Injection

Provider là bất kỳ class nào được đánh dấu @Injectable() và khai báo trong providers của module. Nest tạo instance (mặc định là singleton, mỗi app một instance) và inject vào nơi cần qua constructor.

src/cats/cats.service.ts
import { Injectable, NotFoundException } from '@nestjs/common';
import { InjectModel } from '@nestjs/mongoose';
import { Model } from 'mongoose';
import { Cat } from './schemas/cat.schema';

@Injectable()
export class CatsService {
  constructor(@InjectModel(Cat.name) private readonly catModel: Model<Cat>) {}

  async findOne(id: string) {
    const cat = await this.catModel.findById(id).lean();
    if (!cat) throw new NotFoundException(`Cat ${id} not found`);
    return cat;
  }
}

Nest resolve phụ thuộc thế nào

  1. Lúc khởi động, Nest đọc kiểu tham số constructor (TypeScript phát metadata design:paramtypes nhờ emitDecoratorMetadata).
  2. Kiểu đó chính là token. Nest tìm provider có token tương ứng trong module hiện tại, rồi trong các module được import (chỉ những gì chúng exports).
  3. Nếu chưa có instance thì tạo, đệ quy cho phụ thuộc của nó, rồi cache lại.

Vì token lấy từ kiểu runtime, bạn không thể inject bằng interface hay import type. Khi đó dùng token chuỗi/Symbol với @Inject(), hoặc dùng abstract class làm token (xem Repository pattern).

export const PAYMENT_GATEWAY = Symbol('PAYMENT_GATEWAY');

@Injectable()
export class CheckoutService {
  constructor(
    @Inject(PAYMENT_GATEWAY) private readonly gateway: PaymentGateway, // token Symbol
    @Optional() private readonly metrics?: MetricsService,             // không có cũng không lỗi
  ) {}
}
Lỗi hay gặp

Nest can't resolve dependencies of the CatsService (?): dấu ? chỉ vị trí tham số không resolve được. Thường do (1) quên thêm provider vào module, (2) module chứa provider chưa exports nó, (3) module hiện tại chưa imports module kia, hoặc (4) circular import khiến kiểu là undefined.

Modules

Module là đơn vị tổ chức code. Metadata của @Module() có bốn khóa:

  imports: [MongooseModule.forFeature([{ name: Cat.name, schema: CatSchema }])],
  controllers: [CatsController],
  providers: [CatsService, CatsRepository],
  exports: [CatsService],          // module khác import CatsModule sẽ dùng được CatsService
})

Đóng gói (encapsulation)

Provider mặc định là "private" trong module. Muốn dùng CatsService trong OrdersModule, bạn phải export ở CatsModule và import CatsModule trong OrdersModule. Đừng khai báo lại CatsService trong providers của module khác: làm vậy tạo ra instance thứ hai, mất tính singleton.

Re-export và module dùng chung

@Module({
  imports: [DatabaseModule, RedisModule],
  exports: [DatabaseModule, RedisModule],   // ai import CoreModule sẽ có luôn cả hai
})
export class CoreModule {}

Global module

@Global() khiến các export của module có mặt ở mọi nơi mà không cần import. Hợp với thứ thật sự dùng khắp nơi như config, logger, Redis client. Đừng lạm dụng: global làm mất dấu vết phụ thuộc và khó test.

@Global()
@Module({ providers: [RedisService], exports: [RedisService] })
export class RedisModule {}

Module có thể nhận cấu hình lúc import (dynamic module, như MongooseModule.forRoot(uri)). Phần này được trình bày riêng ở mục Dynamic modules.

Middleware

Middleware chạy trước guard, khi Nest chưa xác định handler nào sẽ xử lý. Vì vậy middleware không biết controller/method đích, không đọc được metadata của decorator. Dùng nó cho việc cấp thấp: gắn request-id, log thô, parse body, CORS tùy biến.

src/common/request-id.middleware.ts
import { Injectable, NestMiddleware } from '@nestjs/common';
import { randomUUID } from 'node:crypto';
import { NextFunction, Request, Response } from 'express';

@Injectable()
export class RequestIdMiddleware implements NestMiddleware {
  use(req: Request, res: Response, next: NextFunction) {
    const id = (req.headers['x-request-id'] as string) ?? randomUUID();
    req.headers['x-request-id'] = id;
    res.setHeader('x-request-id', id);
    next();                       // quên gọi next() thì request treo
  }
}

// middleware dạng hàm: không cần DI thì nên dùng dạng này
export function timing(req: Request, res: Response, next: NextFunction) {
  const start = Date.now();
  res.on('finish', () => console.log(`${req.method} ${req.originalUrl} ${Date.now() - start}ms`));
  next();
}

Middleware không khai báo trong @Module() mà đăng ký bằng method configure() của module (implement NestModule):

@Module({ controllers: [CatsController] })
export class AppModule implements NestModule {
  configure(consumer: MiddlewareConsumer) {
    consumer
      .apply(RequestIdMiddleware, timing)
      .exclude({ path: 'health', method: RequestMethod.GET })
      .forRoutes('{*splat}');          // mọi route (cú pháp Express 5)

    consumer
      .apply(ShopifyHmacMiddleware)
      .forRoutes({ path: 'webhooks/*path', method: RequestMethod.POST }, WebhooksController);
  }
}
  • forRoutes nhận chuỗi path, object { path, method } hoặc class controller.
  • Middleware global không cần DI: app.use(timing) trong main.ts.
  • Exception ném ra trong middleware chỉ được xử lý bởi exception filter global.

Nền tảng

Exception filters

Nest có sẵn một exception layer toàn cục. Exception là HttpException (hoặc lớp con) được trả về đúng status và body; mọi lỗi khác trở thành 500 { "statusCode": 500, "message": "Internal server error" }.

Ném lỗi HTTP

throw new HttpException('Forbidden', HttpStatus.FORBIDDEN);
// → { "statusCode": 403, "message": "Forbidden" }

throw new HttpException({ code: 'QUOTA_EXCEEDED', limit: 1000 }, 429);
// object thay thế toàn bộ body

throw new BadRequestException('Email đã tồn tại', {
  cause: err,                      // chỉ dùng để log, không gửi cho client
  description: 'Duplicate email',  // điền vào trường "error"
});
// → { "statusCode": 400, "message": "Email đã tồn tại", "error": "Duplicate email" }

Các exception dựng sẵn trong @nestjs/common: BadRequestException, UnauthorizedException, ForbiddenException, NotFoundException, MethodNotAllowedException, NotAcceptableException, RequestTimeoutException, ConflictException, GoneException, PreconditionFailedException, PayloadTooLargeException, UnsupportedMediaTypeException, UnprocessableEntityException, ImATeapotException, MisdirectedException, InternalServerErrorException, NotImplementedException, BadGatewayException, ServiceUnavailableException, GatewayTimeoutException, HttpVersionNotSupportedException.

Viết filter riêng

Filter implement ExceptionFilter, method catch(exception, host) nhận exception và ArgumentsHost để lấy request/response. @Catch(Type) giới hạn loại exception; @Catch() rỗng bắt tất cả.

src/common/all-exceptions.filter.ts
import { ArgumentsHost, Catch, ExceptionFilter, HttpException, HttpStatus, Logger } from '@nestjs/common';
import { HttpAdapterHost } from '@nestjs/core';

@Catch()
export class AllExceptionsFilter implements ExceptionFilter {
  private readonly logger = new Logger(AllExceptionsFilter.name);

  constructor(private readonly adapterHost: HttpAdapterHost) {}

  catch(exception: unknown, host: ArgumentsHost) {
    const { httpAdapter } = this.adapterHost;       // dùng adapter để chạy được cả Express lẫn Fastify
    const ctx = host.switchToHttp();
    const req = ctx.getRequest();

    const status = exception instanceof HttpException
      ? exception.getStatus()
      : HttpStatus.INTERNAL_SERVER_ERROR;

    const body = exception instanceof HttpException
      ? exception.getResponse()
      : { message: 'Internal server error' };

    if (status >= 500) this.logger.error(exception);

    httpAdapter.reply(ctx.getResponse(), {
      success: false,
      statusCode: status,
      path: httpAdapter.getRequestUrl(req),
      timestamp: new Date().toISOString(),
      error: body,
    }, status);
  }
}

Gắn filter: @UseFilters(HttpExceptionFilter) trên method/controller, hoặc toàn cục bằng { provide: APP_FILTER, useClass: AllExceptionsFilter }. Muốn giữ hành vi mặc định và chỉ thêm chút logic, kế thừa BaseExceptionFilter rồi gọi super.catch().

Lưu ý
  • app.useGlobalFilters() không áp dụng cho WebSocket gateway và microservice trong hybrid app.
  • Filter không chạy nối tiếp: filter cấp route đã bắt thì filter global không thấy exception đó.
  • Trên Fastify dùng response.send() thay vì response.json().

import { ArgumentMetadata, BadRequestException, Injectable, PipeTransform } from '@nestjs/common';
import { Types } from 'mongoose';

@Injectable()
export class ParseObjectIdPipe implements PipeTransform<string, Types.ObjectId> {
  transform(value: string, metadata: ArgumentMetadata) {

Guards

Guard có một trách nhiệm: trả lời "request này có được đi tiếp không". Khác middleware, guard có ExecutionContext nên biết handler và controller đích, đọc được metadata do decorator gắn. Vì vậy xác thực và phân quyền đặt ở guard.

src/auth/roles.decorator.ts
import { Reflector } from '@nestjs/core';

export type Role = 'admin' | 'staff' | 'merchant';
export const Roles = Reflector.createDecorator<Role[]>();   // tạo decorator có kiểu
src/auth/roles.guard.ts
import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';
import { Reflector } from '@nestjs/core';
import { Roles } from './roles.decorator';

@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private readonly reflector: Reflector) {}

  canActivate(context: ExecutionContext): boolean {
    // ưu tiên metadata trên method, nếu không có thì lấy trên class
    const required = this.reflector.getAllAndOverride(Roles, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (!required?.length) return true;

    const { user } = context.switchToHttp().getRequest();
    return required.some((role) => user?.roles?.includes(role));
  }
}
@Controller('settings')
@UseGuards(AuthGuard, RolesGuard)
export class SettingsController {
  @Patch()
  @Roles(['admin'])
  update(@Body() dto: UpdateSettingsDto) {}
}
  • Guard trả false → Nest ném ForbiddenException (403, "Forbidden resource"). Muốn 401 hoặc message khác thì tự throw.
  • canActivate có thể trả boolean, Promise<boolean> hoặc Observable<boolean>.
  • Nhiều APP_GUARD chạy theo thứ tự đăng ký. Ví dụ đầy đủ về JWT ở mục Bảo mật.

Interceptors

Interceptor bọc quanh lời gọi handler theo kiểu AOP. Method intercept(context, next) chạy logic trước, gọi next.handle() để thực thi handler (trả về Observable), rồi dùng toán tử RxJS để xử lý kết quả. Không gọi next.handle() thì handler không chạy.

Đo thời gian xử lý

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  private readonly logger = new Logger('HTTP');

  intercept(context: ExecutionContext, next: CallHandler): Observable<unknown> {
    const req = context.switchToHttp().getRequest();
    const start = Date.now();
    return next.handle().pipe(
      finalize(() => this.logger.log(`${req.method} ${req.url} ${Date.now() - start}ms`)),
    );
  }
}

Bọc response theo một format chung

export interface Envelope<T> { success: true; data: T }

@Injectable()
export class ResponseInterceptor<T> implements NestInterceptor<T, Envelope<T>> {
  intercept(_: ExecutionContext, next: CallHandler<T>): Observable<Envelope<T>> {
    return next.handle().pipe(map((data) => ({ success: true, data })));
  }
}

Đổi exception và đặt timeout

@Injectable()
export class TimeoutInterceptor implements NestInterceptor {
  intercept(_: ExecutionContext, next: CallHandler) {
    return next.handle().pipe(
      timeout(5000),
      catchError((err) =>
        err instanceof TimeoutError
          ? throwError(() => new RequestTimeoutException())
          : throwError(() => err),
      ),
    );
  }
}

Bỏ qua handler (cache)

@Injectable()
export class SimpleCacheInterceptor implements NestInterceptor {
  constructor(private readonly cache: CacheService) {}

  async intercept(ctx: ExecutionContext, next: CallHandler) {
    const key = ctx.switchToHttp().getRequest().url;
    const hit = await this.cache.get(key);
    if (hit) return of(hit);                       // trả luôn, handler không chạy
    return next.handle().pipe(tap((data) => this.cache.set(key, data, 60_000)));
  }
}
Ghi nhớ

tap không chạy khi handler lỗi. Cần dọn dẹp trong mọi trường hợp thì dùng finalize. Unsubscribe do timeout không hủy được công việc handler đã bắt đầu.

Circular dependency, ModuleRef và lazy loading

Phụ thuộc vòng

Khi A cần B và B cần A, TypeScript import ra undefined tại thời điểm decorator chạy. Giải pháp tạm là forwardRef ở cả hai phía:

// provider
@Injectable()
export class OrdersService {
  constructor(@Inject(forwardRef(() => CustomersService)) private customers: CustomersService) {}
}
@Injectable()
export class CustomersService {
  constructor(@Inject(forwardRef(() => OrdersService)) private orders: OrdersService) {}
}

// module
@Module({ imports: [forwardRef(() => CustomersModule)] })

Nên làm

Vòng phụ thuộc thường là dấu hiệu thiết kế sai. Cách xử lý triệt để: tách phần dùng chung ra module thứ ba, hoặc đổi một chiều gọi thành event (A phát event, B lắng nghe). Tránh file barrel index.ts import qua lại trong cùng thư mục, đây là nguồn circular import phổ biến.

Lifecycle events

Provider, controller và module có thể implement các hook sau:

  1. onModuleInit()Ngay sau khi phụ thuộc của module đã resolve. Hợp để kết nối, warm cache.
  2. onApplicationBootstrap()Khi mọi module đã init, trước khi bắt đầu nhận kết nối.
  3. app.listen()Ứng dụng phục vụ request.
  4. onModuleDestroy()Khi nhận tín hiệu tắt (SIGTERM) hoặc gọi app.close().
  5. beforeApplicationShutdown(signal)Sau khi mọi onModuleDestroy hoàn tất, trước khi đóng kết nối HTTP.
  6. onApplicationShutdown(signal)Sau khi kết nối đã đóng, bước cuối cùng.
@Injectable()
export class RabbitConsumer implements OnModuleInit, OnModuleDestroy, OnApplicationShutdown {
  async onModuleInit() {
    await this.channel.consume('orders', this.handle);
  }
  async onModuleDestroy() {
    await this.channel.cancel(this.consumerTag);   // ngừng nhận message mới
  }
  async onApplicationShutdown(signal?: string) {
    await this.connection.close();
  }
}

// main.ts: bắt buộc nếu muốn hook shutdown chạy khi nhận SIGTERM
app.enableShutdownHooks();

  • Không chạy với provider REQUEST-scoped và module lazy-load.
  • app.close() không tự thoát process; timer còn chạy sẽ giữ process sống.

    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC, [ctx.getHandler(), ctx.getClass()]);
    if (isPublic) return true;

    const req = ctx.switchToHttp().getRequest();
    const [type, token] = req.headers.authorization?.split(' ') ?? [];
    if (type !== 'Bearer' || !token) throw new UnauthorizedException();

    try {
      req.user = await this.jwt.verifyAsync(token);   // gắn user vào request cho guard/handler sau
    } catch {
      throw new UnauthorizedException();
    }
    return true;
  }
}

Response envelope và pagination

Thống nhất hình dạng response cho client: interceptor bọc kết quả thành công, filter bọc lỗi (xem Exception filters), DTO phân trang dùng lại ở mọi danh sách.

export class PageQuery {
  @Type(() => Number) @IsInt() @Min(1) page = 1;
  @Type(() => Number) @IsInt() @Min(1) @Max(100) limit = 20;
  get skip() { return (this.page - 1) * this.limit; }
}

export class Paginated<T> {
  constructor(public items: T[], public total: number, public page: number, public limit: number) {}
}

// repository
async list(shop: string, q: PageQuery) {
  const [items, total] = await Promise.all([
    this.model.find({ shop }).skip(q.skip).limit(q.limit).lean(),
    this.model.countDocuments({ shop }),
  ]);
  return new Paginated(items, total, q.page, q.limit);
}

// interceptor: tách meta phân trang ra khỏi data
@Injectable()
export class EnvelopeInterceptor implements NestInterceptor {
  intercept(_: ExecutionContext, next: CallHandler) {
    return next.handle().pipe(map((res) =>
      res instanceof Paginated
        ? { success: true, data: res.items, meta: { total: res.total, page: res.page, limit: res.limit } }
        : { success: true, data: res },
    ));
  }
}

Patterns

Domain errors tách khỏi HTTP

Service ném lỗi nghiệp vụ không biết gì về HTTP; một filter duy nhất ánh xạ sang status code. Nhờ vậy cùng service dùng được trong HTTP controller, RabbitMQ consumer và cron mà không phải ném NotFoundException trong worker.

export abstract class DomainError extends Error {
  abstract readonly code: string;
  constructor(message: string, readonly details?: Record<string, unknown>) { super(message); }
}
export class QuotaExceededError extends DomainError { readonly code = 'QUOTA_EXCEEDED'; }
export class RuleNotFoundError extends DomainError { readonly code = 'RULE_NOT_FOUND'; }

const STATUS: Record<string, number> = { QUOTA_EXCEEDED: 429, RULE_NOT_FOUND: 404 };

@Catch(DomainError)
export class DomainErrorFilter implements ExceptionFilter {
  constructor(private readonly adapterHost: HttpAdapterHost) {}

  catch(e: DomainError, host: ArgumentsHost) {
    if (host.getType() !== 'http') throw e;                   // RPC/WS tự xử lý
    const status = STATUS[e.code] ?? 400;
    this.adapterHost.httpAdapter.reply(host.switchToHttp().getResponse(),
      { success: false, error: { code: e.code, message: e.message, details: e.details } }, status);
  }
}

Strategy registry

Thay chuỗi switch bằng một bản đồ "loại → implementation" do DI dựng sẵn. Thêm loại mới chỉ cần thêm class, không sửa code cũ.

export abstract class Notifier {
  abstract readonly channel: 'email' | 'slack' | 'sms';
  abstract send(to: string, msg: string): Promise<void>;
}

export const NOTIFIERS = Symbol('NOTIFIERS');

@Module({
  providers: [
    EmailNotifier, SlackNotifier, SmsNotifier,
    {
      provide: NOTIFIERS,
      inject: [EmailNotifier, SlackNotifier, SmsNotifier],
      useFactory: (...list: Notifier[]) => new Map(list.map((n) => [n.channel, n])),
    },
    NotifyService,
  ],
})
export class NotifyModule {}

@Injectable()
export class NotifyService {
  constructor(@Inject(NOTIFIERS) private readonly notifiers: Map<string, Notifier>) {}

  send(channel: string, to: string, msg: string) {
    const n = this.notifiers.get(channel);
    if (!n) throw new BadRequestException(`Kênh ${channel} không hỗ trợ`);
    return n.send(to, msg);
  }
}

Unit of Work / Transactional

Khi một use case ghi nhiều collection, cần transaction. Truyền session qua từng tham số rất dễ quên; plugin @nestjs-cls/transactional cộng đồng lưu transaction trong CLS và cho phép đánh dấu bằng decorator.

npm i @nestjs-cls/transactional @nestjs-cls/transactional-adapter-mongoose
ClsModule.forRoot({
  global: true,
  plugins: [
    new ClsPluginTransactional({
      adapter: new TransactionalAdapterMongoose({ mongooseConnectionToken: getConnectionToken() }),
    }),
  ],
});

@Injectable()
export class OrdersRepository {
  constructor(
    @InjectModel(Order.name) private readonly model: Model<Order>,
    private readonly txHost: TransactionHost<TransactionalAdapterMongoose>,
  ) {}

  create(data: NewOrder) {
    return this.model.create([data], { session: this.txHost.tx });  // tx = ClientSession hiện tại
  }
}

@Injectable()
export class CheckoutService {
  @Transactional()                       // mọi repository bên trong dùng chung một transaction
  async placeOrder(dto: PlaceOrderDto) {
    const [order] = await this.orders.create(dto);
    await this.quota.decrement(dto.shop);
    await this.outbox.add('order.created', { id: order.id });   // xem pattern Outbox
    return order;
  }
}

Transactional outbox

Vấn đề "dual write": ghi DB thành công rồi publish lên RabbitMQ thất bại (hoặc ngược lại) làm hai hệ thống lệch nhau. Outbox giải quyết bằng cách ghi message vào một collection outbox trong cùng transaction với dữ liệu nghiệp vụ; một tiến trình relay đọc outbox và publish, đánh dấu đã gửi. Kết quả là "at-least-once": consumer phải idempotent.

@Schema({ collection: 'outbox', timestamps: true })
export class OutboxMessage {
  @Prop({ required: true }) type: string;
  @Prop({ type: Object, required: true }) payload: Record<string, unknown>;
  @Prop({ default: 'pending', index: true }) status: 'pending' | 'sent';
  @Prop({ default: 0 }) attempts: number;
}

@Injectable()
export class OutboxService {
  constructor(
    @InjectModel(OutboxMessage.name) private readonly model: Model<OutboxMessage>,
    private readonly txHost: TransactionHost<TransactionalAdapterMongoose>,
  ) {}

  add(type: string, payload: Record<string, unknown>) {
    return this.model.create([{ type, payload }], { session: this.txHost.tx });
  }
}

@Injectable()
export class OutboxRelay {
  constructor(
    @InjectModel(OutboxMessage.name) private readonly model: Model<OutboxMessage>,
    private readonly amqp: AmqpConnection,
  ) {}

  @Interval(1_000)
  async flush() {
    const batch = await this.model.find({ status: 'pending' }).sort({ _id: 1 }).limit(100).lean();
    for (const m of batch) {
      await this.amqp.publish('events', m.type, { id: String(m._id), ...m.payload }, { persistent: true });
      await this.model.updateOne({ _id: m._id }, { $set: { status: 'sent' } });
    }
  }
}

Chạy relay ở nhiều instance thì bọc flush() trong distributed lock, hoặc "claim" từng message bằng findOneAndUpdate({ status: 'pending' }, { $set: { status: 'processing' } }). Có thể thay polling bằng MongoDB change streams.

Idempotency

Phía HTTP: Idempotency-Key

Client gửi header Idempotency-Key; server lưu kết quả lần đầu và trả lại đúng kết quả đó cho các lần retry.

@Injectable()
export class IdempotencyInterceptor implements NestInterceptor {
  constructor(@Inject(REDIS) private readonly redis: Redis) {}

  async intercept(ctx: ExecutionContext, next: CallHandler) {
    const req = ctx.switchToHttp().getRequest();
    const key = req.headers['idempotency-key'];
    if (!key) return next.handle();

    const redisKey = `idem:${req.user?.sub ?? 'anon'}:${key}`;
    const acquired = await this.redis.set(redisKey, 'PENDING', 'EX', 86_400, 'NX');
    if (!acquired) {
      const saved = await this.redis.get(redisKey);
      if (saved === 'PENDING') throw new ConflictException('Request với key này đang được xử lý');
      return of(JSON.parse(saved!));                      // trả lại kết quả cũ
    }

    return next.handle().pipe(
      mergeMap(async (res) => {
        await this.redis.set(redisKey, JSON.stringify(res), 'EX', 86_400);
        return res;
      }),
      catchError((err) => from(this.redis.del(redisKey)).pipe(mergeMap(() => throwError(() => err)))),
    );
  }
}

Phía consumer: inbox

Message broker có thể giao trùng. Ghi lại id message đã xử lý với unique index; gặp lỗi trùng khóa thì bỏ qua.

async handle(msg: { id: string; shop: string }) {
  try {
    await this.processed.create({ _id: msg.id, at: new Date() });   // unique theo _id
  } catch (e: any) {
    if (e.code === 11000) return;                                  // đã xử lý rồi
    throw e;
  }
  await this.doWork(msg);
}

Cách đơn giản hơn khi được: thiết kế thao tác tự nhiên là idempotent, như upsert theo khóa tự nhiên (shop + orderId) thay vì insert, hoặc $set thay vì $inc.

Distributed lock

Đảm bảo một cron/relay chỉ chạy trên một instance tại một thời điểm. Khóa Redis với token ngẫu nhiên, chỉ chủ khóa mới được xóa.

const RELEASE = `if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`;

@Injectable()
export class LockService {
  constructor(@Inject(REDIS) private readonly redis: Redis) {}

  async run<T>(name: string, ttlMs: number, fn: () => Promise<T>): Promise<T | null> {
    const key = `lock:${name}`;
    const token = randomUUID();
    const ok = await this.redis.set(key, token, 'PX', ttlMs, 'NX');
    if (!ok) return null;                        // instance khác đang chạy
    try {
      return await fn();
    } finally {
      await this.redis.eval(RELEASE, 1, key, token);
    }
  }
}

@Cron(CronExpression.EVERY_MINUTE)
syncUsage() {
  return this.lock.run('sync-usage', 55_000, () => this.usage.sync());
}

TTL phải dài hơn thời gian chạy dự kiến; job dài thì gia hạn khóa định kỳ. Docs v12 giới thiệu @nestjs/locks với @OnOneInstance() cho đúng việc này.

Modular monolith

Một codebase, một lần deploy, nhưng module có ranh giới như microservice. Khi cần tách service sau này, ranh giới đã sẵn.

  • Mỗi module chỉ exports một "facade" service. Không export repository, model hay schema.
  • Module A không import file nội bộ của module B (../billing/billing.repository). Có thể ép bằng eslint-plugin-boundaries hoặc dependency-cruiser.
  • Ghi chéo giữa module đi qua facade; phản ứng phụ (gửi mail, cập nhật thống kê) đi qua event.
  • Mỗi module sở hữu collection của mình; module khác không query thẳng.
  • Dùng CQRS chỉ khi luồng đọc và ghi khác nhau rõ rệt.
@Module({
  imports: [MongooseModule.forFeature([{ name: Plan.name, schema: PlanSchema }])],
  providers: [BillingService, PlanRepository, ShopifyBillingClient],
  exports: [BillingService],      // chỉ facade được lộ ra ngoài
})
export class BillingModule {}

Graceful shutdown

Khi Kubernetes gửi SIGTERM, ứng dụng nên ngừng nhận việc mới, làm xong việc đang dở, rồi mới đóng kết nối.

// main.ts
const app = await NestFactory.create(AppModule, { forceCloseConnections: true });
app.enableShutdownHooks();

@Injectable()
export class ShutdownState implements BeforeApplicationShutdown {
  shuttingDown = false;
  beforeApplicationShutdown() { this.shuttingDown = true; }   // health readiness trả 503
}

@Injectable()
export class OrdersConsumer implements OnModuleDestroy {
  private inFlight = new Set<Promise<unknown>>();

  async onModuleDestroy() {
    await this.channel.cancel(this.tag);           // 1. ngừng nhận message mới
    await Promise.allSettled([...this.inFlight]);   // 2. đợi message đang xử lý
  }
}
// 3. Mongo/Redis đóng ở onApplicationShutdown của module tương ứng

Thêm preStop sleep vài giây trong manifest Kubernetes để load balancer kịp gỡ pod trước khi app ngừng nhận request.

Checklist trước khi lên production

  • ValidationPipe global với whitelist: true.
  • Biến môi trường được validate lúc khởi động (fail fast).
  • Exception filter global, log lỗi 5xx có stack và request-id.
  • Log dạng JSON, không log token, mật khẩu, PII.
  • Security headers (helmet), CORS whitelist cụ thể, rate limit cho endpoint đăng nhập.
  • app.enableShutdownHooks() và consumer dừng nhận message trong onModuleDestroy.
  • Health check /health (liveness) và kiểm tra DB/Redis (readiness).
  • Index cho mọi query nóng; không synchronize: true với SQL.
  • Cron/relay có khóa phân tán khi chạy nhiều replica.
  • Consumer idempotent, message lỗi đi vào dead-letter queue.
  • Swagger chỉ bật ở môi trường không phải production, hoặc có bảo vệ.
  • Build bằng SWC/tsc, chạy node dist/main, không chạy nest start trong container.

  1. javac biên dịchApp.java → App.class chứa bytecode, độc lập nền tảng.

Pinning

Ở JDK 21–23, virtual thread bị "ghim" vào carrier khi blocking bên trong synchronized, làm mất lợi ích; lời khuyên khi đó là đổi sang ReentrantLock. Từ JDK 24 vấn đề này đã được sửa; chỉ còn ghim khi gọi native method hoặc foreign function. Theo dõi bằng sự kiện JFR jdk.VirtualThreadPinned.

// giới hạn 20 request đồng thời tới API ngoài dù có 10.000 virtual thread
private final Semaphore permits = new Semaphore(20);

IpInfo lookup(String ip) throws InterruptedException {
    permits.acquire();
    try { return client.get(ip); } finally { permits.release(); }
}

Đồng bộ hóa và Java Memory Model

Khi nhiều thread cùng đọc/ghi một biến, cần hai bảo đảm: nguyên tử (không bị chen ngang giữa chừng) và khả kiến (thread khác thấy giá trị mới). Java Memory Model định nghĩa quan hệ happens-before: unlock trước lock, ghi volatile trước đọc volatile, Thread.start() trước mọi hành động trong thread đó.

// 1. synchronized: nguyên tử + khả kiến
private int count;
public synchronized void inc() { count++; }

// 2. volatile: chỉ khả kiến, KHÔNG nguyên tử (count++ vẫn sai)
private volatile boolean running = true;
public void stop() { running = false; }

// 3. atomic: nguyên tử không cần khóa
private final AtomicLong requests = new AtomicLong();
requests.incrementAndGet();
private final LongAdder hits = new LongAdder();          // nhanh hơn khi ghi rất nhiều
hits.increment();

// 4. ConcurrentHashMap: thao tác gộp nguyên tử
ConcurrentHashMap<String, LongAdder> perIp = new ConcurrentHashMap<>();
perIp.computeIfAbsent(ip, k -> new LongAdder()).increment();
perIp.merge(shop, 1L, Long::sum);

// 5. lock tường minh: có tryLock, timeout, nhiều condition
private final ReentrantLock lock = new ReentrantLock();
if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
    try { refreshToken(); } finally { lock.unlock(); }
}
ReadWriteLock rw = new ReentrantReadWriteLock();         // nhiều reader, một writer

// 6. điều phối
CountDownLatch ready = new CountDownLatch(3);            // chờ 3 sự kiện
ready.countDown(); ready.await();

Cách an toàn nhất là không chia sẻ trạng thái có thể sửa: dùng object bất biến (record), truyền dữ liệu qua BlockingQueue, hoặc giới hạn trạng thái trong một thread. Ưu tiên tiện ích của java.util.concurrent hơn wait()/notify().

Coi một nhóm tác vụ con như một đơn vị: nếu một tác vụ lỗi thì các tác vụ còn lại bị hủy, và không tác vụ nào "rò" ra ngoài block. Tới JDK 27 vẫn là preview (cần --enable-preview), API có thể còn đổi.

record Profile(User user, List<Order> orders) {}

Profile load(long id) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {        // mặc định: tất cả phải thành công

}

Builder

Dùng khi object có nhiều tham số tùy chọn: tránh constructor dài với cả chục tham số cùng kiểu dễ truyền nhầm thứ tự.

public record HttpRetryPolicy(int maxAttempts, Duration baseDelay, Duration maxDelay,
                              Set<Integer> retryOn, boolean jitter) {

    public static Builder builder() { return new Builder(); }

    public static final class Builder {
        private int maxAttempts = 3;                          // giá trị mặc định
        private Duration baseDelay = Duration.ofMillis(200);
        private Duration maxDelay = Duration.ofSeconds(10);
        private Set<Integer> retryOn = Set.of(429, 502, 503, 504);
        private boolean jitter = true;

        public Builder maxAttempts(int v) { this.maxAttempts = v; return this; }
        public Builder baseDelay(Duration v) { this.baseDelay = v; return this; }
        public Builder maxDelay(Duration v) { this.maxDelay = v; return this; }
        public Builder retryOn(Integer... codes) { this.retryOn = Set.of(codes); return this; }
        public Builder jitter(boolean v) { this.jitter = v; return this; }

        public HttpRetryPolicy build() {
            if (maxAttempts < 1) throw new IllegalStateException("maxAttempts >= 1");
            return new HttpRetryPolicy(maxAttempts, baseDelay, maxDelay, retryOn, jitter);
        }
    }
}

public final class CachingGeoLookup implements GeoLookup {
    private final GeoLookup inner;
    private final Map<String, GeoInfo> cache = Collections.synchronizedMap(

    }
}

    private final GeoLookup inner;
    private final Timer timer;
    public TimedGeoLookup(GeoLookup inner, Timer timer) { this.inner = inner; this.timer = timer; }
    @Override public GeoInfo lookup(String ip) {
        long t = System.nanoTime();
        try { return inner.lookup(ip); } finally { timer.record(System.nanoTime() - t); }
    }
}

Design patterns

Proxy và dynamic proxy

Proxy đứng thay object thật để kiểm soát truy cập: khởi tạo lười, kiểm tra quyền, gọi từ xa, transaction. Java tạo được proxy lúc runtime cho mọi interface; Spring dùng chính cơ chế này cho @Transactional và AOP.

@SuppressWarnings("unchecked")
static <T> T logged(T target, Class<T> iface) {
    InvocationHandler handler = (proxy, method, args) -> {
        long start = System.nanoTime();
        try {
            return method.invoke(target, args);
        } catch (InvocationTargetException e) {
            throw e.getCause();                                     // ném lỗi gốc, không phải lỗi bọc
        } finally {
            System.out.printf("%s.%s %d µs%n", iface.getSimpleName(), method.getName(),
                              (System.nanoTime() - start) / 1_000);
        }
    };
    return (T) Proxy.newProxyInstance(iface.getClassLoader(), new Class<?>[] { iface }, handler);
}

GeoLookup geo = logged(new MaxMindGeoAdapter(reader), GeoLookup.class);
Self-invocation

Proxy chỉ chặn lời gọi đi qua proxy. Method trong cùng class gọi nhau bằng this.foo() thì bỏ qua proxy, nên @Transactional hay @Cacheable của Spring không có tác dụng trong trường hợp đó.

public final class EventBus<E> {

        }
    }

Mỗi handler quyết định xử lý hay chuyển cho handler tiếp theo. Đây chính là mô hình của Servlet Filter và middleware trong NestJS/Express.

@FunctionalInterface
interface Check {
    Optional<Verdict> apply(Visitor v);                 // empty = không kết luận, chuyển tiếp
}

final class CheckChain {
    private final List<Check> checks;
    CheckChain(List<Check> checks) { this.checks = List.copyOf(checks); }

    Verdict evaluate(Visitor v) {
        for (Check c : checks) {
            Optional<Verdict> r = c.apply(v);
            if (r.isPresent()) return r.get();          // handler đầu tiên có kết luận thắng
        }
        return Verdict.ALLOW;
    }
}

Design patterns

Visitor và sealed + switch

Visitor cổ điển cần method accept(Visitor) ở mọi class và một interface visitor có method cho từng loại. Với Java 21, sealed interface + pattern matching switch đạt cùng mục đích (thêm thao tác mới mà không sửa các class) với ít code hơn, và compiler báo lỗi khi thiếu trường hợp.

sealed interface Expr permits Num, Add, Mul, Neg {}
record Num(double v) implements Expr {}
record Add(Expr l, Expr r) implements Expr {}
record Mul(Expr l, Expr r) implements Expr {}
record Neg(Expr e) implements Expr {}

// "visitor" 1: tính giá trị
static double eval(Expr e) {
    return switch (e) {
        case Num(var v) -> v;
        case Add(var l, var r) -> eval(l) + eval(r);
        case Mul(var l, var r) -> eval(l) * eval(r);
        case Neg(var x) -> -eval(x);
    };
}

// "visitor" 2: in ra chuỗi, không cần sửa các record
static String show(Expr e) {
    return switch (e) {
        case Num(var v) -> String.valueOf(v);
        case Add(var l, var r) -> "(" + show(l) + " + " + show(r) + ")";
        case Mul(var l, var r) -> show(l) + " * " + show(r);
        case Neg(var x) -> "-" + show(x);
    };
}

Đánh đổi: thêm thao tác mới rất dễ, nhưng thêm loại mới phải sửa mọi switch (compiler sẽ chỉ ra chỗ cần sửa). Khi tập loại mở cho bên ngoài mở rộng, dùng đa hình bằng method trong interface.

Pattern hiện đại

Retry, Circuit Breaker, Bulkhead

Gọi dịch vụ ngoài thì phải tính tới lỗi tạm thời. Ba pattern bổ trợ nhau:

Retry

Thử lại lỗi tạm thời với backoff mũ + jitter. Chỉ retry thao tác idempotent.

Circuit Breaker

Lỗi vượt ngưỡng thì "ngắt mạch" (open), trả lỗi ngay; sau một lúc thử lại (half-open) rồi đóng (closed).

Bulkhead

Giới hạn số lời gọi đồng thời tới mỗi dịch vụ để một dịch vụ chậm không nuốt hết tài nguyên.

static <T> T retry(Callable<T> call, HttpRetryPolicy p) throws Exception {
    for (int attempt = 1; ; attempt++) {
        try {
            return call.call();
        } catch (IOException e) {
            if (attempt >= p.maxAttempts()) throw e;
            long cap = Math.min(p.maxDelay().toMillis(), p.baseDelay().toMillis() << (attempt - 1));
            long sleep = p.jitter() ? ThreadLocalRandom.current().nextLong(cap + 1) : cap;
            Thread.sleep(Duration.ofMillis(sleep));     // rẻ trên virtual thread
        }
    }
}

Production nên dùng Resilience4j lib: có sẵn Retry, CircuitBreaker, Bulkhead, RateLimiter, TimeLimiter, ghép được với nhau và tích hợp Spring Boot bằng annotation.

Producer–Consumer

Tách nơi sinh việc và nơi xử lý bằng một hàng đợi có giới hạn. Hàng đợi đầy thì producer bị chặn lại (back-pressure), tránh tràn bộ nhớ.

BlockingQueue<Visit> queue = new ArrayBlockingQueue<>(10_000);

// producer: request handler
void onVisit(Visit v) {
    if (!queue.offer(v)) metrics.inc("visits.dropped");   // không chặn request: bỏ khi đầy
}

// consumer: gom theo lô rồi ghi DB
Thread.ofVirtual().start(() -> {
    List<Visit> batch = new ArrayList<>(500);
    while (!Thread.currentThread().isInterrupted()) {
        try {
            batch.add(queue.take());                         // chờ có phần tử
            queue.drainTo(batch, 499);                       // lấy thêm những gì đang có
            repo.insertMany(batch);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();              // giữ cờ interrupt rồi thoát
        } finally {
            batch.clear();
        }
    }
});

Tra cứu

Nguyên tắc viết Java tốt

Tổng hợp từ "Effective Java" (Joshua Bloch) và kinh nghiệm cộng đồng:

  • Cân nhắc static factory thay constructor; dùng builder khi có nhiều tham số tùy chọn; singleton thì dùng enum.
  • Giảm tối đa khả năng sửa đổi: field final, class final hoặc record, sao chép phòng thủ collection.
  • Ưu tiên composition hơn kế thừa; thiết kế cho kế thừa hoặc cấm nó (final, sealed).
  • Override equals thì override cả hashCode.
  • Khai báo biến theo interface: List<X> xs = new ArrayList<>().
  • Trả collection rỗng, đừng trả null. Optional chỉ dùng cho kiểu trả về.
  • Kiểm tra tham số đầu method: Objects.requireNonNull, Objects.checkIndex.
  • Dùng exception đúng loại; không nuốt lỗi; giữ nguyên cause khi bọc lại.
  • Ưu tiên tiện ích của java.util.concurrent hơn wait/notify; ưu tiên dữ liệu bất biến khi chia sẻ giữa các thread.
  • Tiền tệ dùng BigDecimal tạo từ chuỗi (new BigDecimal("0.10")), không dùng double.
